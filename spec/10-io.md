# 10. IO Model

This section defines how Cranelisp tracks and performs side effects. IO in Cranelisp is modeled as an algebraic data type that wraps effectful results. The type system ensures that side effects are visible in function signatures, preventing accidental mixing of pure and effectful code.

## 10.1 IO Type [Tested tests/spec_10_io::bind_constructor_rejected]

The `IO` type is an algebraic data type with three constructors:

```clojure
(deftype (IO a)
  (Pure [:a ioval])       ; tag=0: completed value
  (Effect [:a thunk])     ; tag=1: deferred effect (opaque thunk pointer)
  (Bind ...))             ; tag=2: chain (internal)
```

This definition is **compiler-seeded** -- it is registered in the `primitives` module by the compiler itself, not by user code or standard library code. It is available in all programs without an explicit import.

The `Bind` constructor is marked **internal** -- it is visible in REPL introspection (`/info IO`) but cannot be constructed or pattern-matched by user code. It has an existential type that HM inference cannot express. In the sketch above the `...` **elides `Bind`'s field list** (which is exactly what cannot be written in surface syntax); it is not an empty constructor form, which would be a parse error under §5.2.2. `Bind`'s runtime fields are given concretely in §10.1.3.

`IO a` represents a deferred computation that will produce a value of type `a` when forced. For example:

- `IO Int` -- a deferred computation that produces an integer
- `IO String` -- a deferred computation that produces a string
- `IO (Option Int)` -- a deferred computation that produces an optional integer

### 10.1.1 Type System Integration [Tested tests/spec_10_io::io_propagates_into_inferred_return_type]

`IO` participates in the type system as an ordinary ADT. There are no special type-checking rules for `IO` -- its effect-tracking properties emerge from standard Hindley-Milner inference:

- A function that calls a platform operation (e.g., `print`) returns `IO` because the platform operation returns `IO`, and the function's return type unifies with the call result.
- A function that does not call any IO operation has no `IO` in its return type.
- A function that calls an IO-returning function inherits `IO` in its own return type.

This means that **IO propagates upward through the call graph automatically** via type inference, without any special rules or annotations.

### 10.1.2 Purity Guarantee [Tested+Neg tests/spec_10_io::io_value_in_pure_position_is_type_error_neg]

A function whose type does not contain `IO` is guaranteed to be pure -- it cannot have performed any side effects. This is enforced by the type system: calling an IO-returning function from a pure context would force `IO` into the pure function's return type, producing a type mismatch if the call site expects a non-IO result.

```clojure
(defn add [x y] (+ x y))         ; add :: (Fn [Int Int] Int) -- pure
(defn greet [name]                ; greet :: (Fn [String] (IO Int)) -- effectful
  (print (str-concat "hello " name)))
```

### 10.1.3 Runtime Representation [S10]

At runtime, `IO a` values are heap-allocated tagged nodes:

- `Pure`: `[tag=0, value]` -- 16 bytes. A completed value.
- `Effect`: `[tag=1, thunk_ptr, resource_token]` -- 24 bytes. A deferred effect containing a double-boxed Rust closure (`Box<Box<dyn FnOnce() -> i64>>`) and a resource token (0 for unscheduled effects; reserved for auto-scheduling in §10.12). [Verified S23: runtime layout in `cranelisp-runtime` and `cranelisp-platform` matches spec; resource_token=0 for all current effects; Par node (tag=3) deferred to S25.]
- `Bind`: `[tag=2, inner_io_ptr, cont_closure_ptr]` -- 24 bytes. A chain linking an inner IO computation with a continuation closure.

These nodes form a tree that the runtime interprets via a trampoline loop (Section 10.8).

## 10.2 `pure` [Tested tests/spec_10_io::pure_int_unwraps_inline]

```
pure :: (Fn [a] (IO a))
```

`pure` is an ordinary library function that wraps a value in a `Pure` constructor, creating a completed IO value.

### 10.2.1 Example Definition [S10]

```clojure
(defn pure "Lift a value into IO" [x] (Pure x))
```

### 10.2.2 Purpose [S10]

`pure` is required when an expression needs to produce an `IO a` value without actually performing a side effect. The most common use case is mixing pure and effectful branches in an `if` expression, where both branches MUST have the same type:

```clojure
;; ERROR: branch types differ -- IO Int vs Int
(if (> x 0)
  (print (show x))    ; IO Int
  0)                   ; Int

;; OK: both branches return IO Int
(if (> x 0)
  (print (show x))    ; IO Int
  (pure 0))           ; IO Int
```

### 10.2.3 Examples [Tested tests/spec_10_io::pure_bool_unwraps_inline]

```clojure
(pure 42)              ; => Pure(42) :: (IO Int)
(pure "hello")         ; => Pure("hello") :: (IO String)
(pure true)            ; => Pure(true) :: (IO Bool)
(pure None)            ; => Pure(None) :: (IO (Option a))
```

`pure` is NOT a special form -- it is an ordinary function. It can be passed as a value, partially applied, or used anywhere a function `(Fn [a] (IO a))` is expected.

## 10.3 `bind` [Tested tests/spec_10_io::bind_triple_chain]

```
bind :: (Fn [(IO a) (Fn [a] (IO b))] (IO b))
```

`bind` is an **inline primitive** that constructs a `Bind` node in the IO task tree, deferring the actual chaining until the trampoline forces the tree (Section 10.8).

### 10.3.1 Semantics [Tested tests/spec_10_io::bind_pure_to_pure_plus_one]

`bind` allocates a `Bind` node containing the IO computation and the continuation closure. No execution happens at the call site -- the chain is purely structural. The trampoline interprets `Bind` nodes by processing the inner IO computation first, then passing its result to the continuation.

At the Cranelift IR level, `bind` allocates 24 bytes (`[tag=2, io_ptr, cont_ptr]`) and stores the two arguments. This is an inline primitive, not a library function -- no function call overhead.

### 10.3.3 Examples [Tested tests/spec_10_io::bind_nested_chain]

```clojure
;; Extract print's return value and use it
(bind (print "hello")
  (fn [result] (pure (+ result 1))))    ; result is the Int returned by print

;; Chain multiple IO actions
(bind (print "first")
  (fn [_]
    (bind (print "second")
      (fn [_] (print "third")))))
```

The nested continuation style can become deeply indented. The `bind!` macro (Section 10.5) provides syntactic sugar for flattening these chains.

## 10.4 Expression Sequencing (Example: `do` Macro) [Tested tests/spec_11_stdlib::macro_do_returns_last]

```clojure
(do expr1 expr2 ... exprN)
```

`do` is a library macro (not a language requirement) that sequences expressions, discarding intermediate results. It returns the value of the last expression.

### 10.4.1 Expansion [Tested tests/spec_platforms::bind_chain_print_sequence_with_pure_terminator_emits_all]

`do` expands to nested `bind` calls with anonymous continuation closures:

```clojure
(do e1 e2 e3)
;; expands to:
(bind e1 (fn [_] (bind e2 (fn [_] e3))))
```

The general form:

```clojure
(do e1 e2 ... en)
;; expands to:
(bind e1 (fn [_] (bind e2 (fn [_] ... (bind e(n-1) (fn [_] en)) ...))))
```

### 10.4.2 Semantics [S10]

`do` is **IO-specific** -- all expressions MUST have type `IO _`. Each intermediate expression's result is discarded (bound to `_` in the continuation). The type of the `do` block is the type of the last expression.

For pure expression sequencing, use `let [_ expr1] expr2` instead.

```clojure
;; IO context: all expressions return IO, block type is IO Int
(defn main []
  (do
    (print "hello")          ; IO Int, result discarded
    (print "world")          ; IO Int, result discarded
    (print "done")))         ; IO Int, returned
```

### 10.4.3 Examples [S10]

```clojure
(defn greet-twice [name]
  (do
    (print (str-concat "hello " name))
    (print (str-concat "goodbye " name))))

(defn main []
  (do
    (print (show 42))
    (print (show 100))))
```

## 10.5 Monadic Bind Sugar (Example: `bind!` Macro) [Tested tests/spec_11_stdlib::macro_bind_bang_single_binding]

```clojure
(bind! [name1 io-expr1
        name2 io-expr2
        ...]
  body)
```

`bind!` is a library macro (not a language requirement) that provides syntactic sugar for monadic bind chains. It desugars to nested `bind`/`fn` calls, making sequential IO operations with named intermediate results readable.

### 10.5.1 Expansion [S10]

Single binding:

```clojure
(bind! [x (read-line)]
  (print x))
;; expands to:
(bind (read-line) (fn [x] (print x)))
```

Multiple bindings:

```clojure
(bind! [line (read-line)
        result (pure (parse-int line))]
  (match result
    [(Some n) (pure n)
     None (pure 0)]))
;; expands to:
(bind (read-line) (fn [line]
  (bind (pure (parse-int line)) (fn [result]
    (match result
      [(Some n) (pure n)
       None (pure 0)])))))
```

### 10.5.2 Semantics [Tested tests/spec_11_stdlib::macro_bind_bang_sequential_reference]

Each binding pair `name io-expr` evaluates `io-expr` (which MUST produce an `IO a`), extracts the inner value via `bind`, and makes it available as `name` in subsequent bindings and the body.

The bindings are evaluated left-to-right. Each binding can reference names introduced by earlier bindings. The body expression is evaluated in the scope of all bindings and MUST produce an `IO b` value.

### 10.5.3 Comparison with `do` [S10]

`do` discards intermediate values -- use it when you only care about sequencing effects. `bind!` names intermediate values -- use it when you need the results of earlier IO operations:

```clojure
;; do: sequence effects, discard results
(do
  (print "enter name:")
  (print "enter age:"))

;; bind!: sequence effects, use results
(bind! [name (read-line)
        age (read-line)]
  (print (str-concat "hello " (str-concat name (str-concat " age " age)))))
```

## 10.6 Entry Point [Tested+Neg tests/spec_10_io.rs::batch_main_pure_int_return_is_rejected]

Batch programs MUST define a function named `main` with no parameters. The return type of `main` MUST be `IO _` (IO of any type):

```
main :: (Fn [] (IO _))
```

The `main` function is the entry point for batch-mode execution. When a program is run with `cranelisp --run file.cl`, the compiler locates and invokes `main` after compilation.

### 10.6.1 Exit Code [Tested+Neg tests/spec_10_io.rs::batch_main_pure_int_return_is_rejected]

The inner value of `main`'s return is the program's exit code. When `main` returns `IO Int`, the integer value is used as the process exit code. Other inner types produce implementation-defined exit behavior.

```clojure
(defn main []
  (do
    (print "hello")
    (pure 0)))          ; exit code 0

(defn main []
  (print "hello"))      ; print returns IO Int (0), so exit code is 0
```

### 10.6.2 REPL Mode [Tested tests/spec_10_io::repl_pure_int_unwraps]

In REPL mode, there is no `main` function requirement. Expressions are evaluated interactively. IO expressions are forced via the trampoline before display, so effects execute and the inner result is shown:

```
user> (print "hello")
hello
0 :: (IO Int)
```

### 10.6.3 Mode-Output Equivalence [Tested tests/output_equivalence::output_equiv_single_print]

A program's **observable output is identical across all run modes**. The same program, executed under `--run` (JIT), under a `--link`-produced standalone binary, or by entering its forms at the REPL, MUST produce byte-for-byte identical observable effects (the stream of `print` / `read-line` and other platform-effect interactions, in the same order). The run mode determines only *how* the program is built and invoked — not *what* it observably does. The IO task tree and its trampoline interpretation (§10.8) are mode-independent, so the effects forced are the same in every mode. (This is the IO-specific instance of the general cross-mode equivalence guarantee; cf. the `(trace ...)` "behaves identically across modes" guarantee at §[4.12.9](04-expressions.md#4129-build-mode-availability).)

## 10.7 Effect Tracking [Tested tests/spec_10_io::defn_returning_pure_displays_fn_type]

IO effects are tracked entirely through the type system, using standard type inference. There are no special annotations, keywords, or compiler flags for effect tracking.

### 10.7.1 Propagation [Tested tests/spec_10_io::defn_returning_pure_displays_fn_type]

When a function calls an IO-returning operation, the IO type propagates to the function's own return type:

```clojure
(defn greet [x]          ; inferred: (Fn [String] (IO Int))
  (print x))

(defn greet-num [x]      ; inferred: (Fn [Int] (IO Int))
  (print (show x)))

(defn double-greet [x]   ; inferred: (Fn [Int] (IO Int))
  (do
    (print (show x))
    (print (show (+ x 1)))))
```

Pure functions remain pure:

```clojure
(defn add [x y]          ; inferred: (Fn [Int Int] Int)
  (+ x y))

(defn double [x]         ; inferred: (Fn [Int] Int)
  (* x 2))
```

### 10.7.2 Branch Consistency [Tested tests/spec_10_io::if_both_branches_io]

Both branches of an `if` expression MUST have the same type. When one branch performs IO and the other does not, the pure branch MUST be wrapped with `pure` to produce a matching `IO` type:

```clojure
;; ERROR: (IO Int) vs Int
(if condition
  (print "yes")
  42)

;; OK: both branches are (IO Int)
(if condition
  (print "yes")
  (pure 42))
```

The same applies to `match` arms -- all arms MUST have the same type, so if any arm performs IO, all arms MUST return IO.

## 10.8 Deferred Execution (Task + Trampoline) [Tested tests/spec_10_io::io_values_deferred]

Cranelisp uses **deferred evaluation** for IO operations. When the program reaches a call to a platform operation, the effect is captured in an `Effect` node but does NOT execute. The effect executes only when the runtime's trampoline loop forces the IO task tree.

```clojure
(some-platform-op "hello")  ; returns Effect(thunk) -- effect not yet performed
```

### 10.8.1 Task Tree Construction [Tested crates/cranelisp-intrinsics/src/io.rs::test_run_io_pure]

IO values are **descriptions of deferred work**, not results:

- A platform operation call returns an `Effect` node containing a closure that executes the effect when forced.
- `(bind io cont)` returns a `Bind` node linking the IO computation with the continuation.
- `(pure 42)` returns a `Pure` node containing the value directly.
- Effects only execute when the trampoline loop processes `Effect` nodes.

```clojure
(let [io (print "hello")]   ; io is an Effect node — nothing printed
  io)                        ; returns the Effect node
;; The effect executes when the runtime forces this IO tree
```

### 10.8.2 Trampoline Interpretation [Tested tests/spec_10_io::run_mode_deep_bind_chain_named_continuation]

The runtime forces the IO task tree using a flat trampoline loop with an explicit continuation stack:

1. **`Pure(val)`**: If continuation stack is empty, return `val`. Otherwise, pop a continuation and apply it to `val`, replacing the current node.
2. **`Effect(thunk)`**: Execute the thunk (this is where the actual side effect happens). Then proceed as with `Pure` using the result.
3. **`Bind(inner, cont)`**: Push `cont` onto the continuation stack and process `inner` next.

This loop is iterative — no recursion, O(1) call stack depth regardless of chain length. IO loops run indefinitely without stack growth.

### 10.8.3 Effect Isolation [S10]

Because effects are deferred, they no longer escape through argument evaluation:

```clojure
(defn choose [p a b] (if p a b))
(defn main [] (choose true (print "a") (print "b")))
```

Both `(print "a")` and `(print "b")` construct `Effect` nodes but do NOT execute. Since `choose` returns only one of them, only that branch's effect is present in the returned IO tree. The trampoline forces only "a" to print.

### 10.8.4 Comparison [S10]

| Property | Cranelisp (Deferred) | Haskell (Lazy) |
|---|---|---|
| When effects execute | When trampoline forces the IO tree | When the runtime interprets the IO action |
| What IO values contain | Descriptions of pending effects | Descriptions of pending effects |
| Effect ordering | Determined by `bind`/`do` chain structure | Determined by data dependencies and `>>=` chains |
| Stack depth | O(1) — trampoline with explicit continuation stack | Implementation-dependent |
| Runtime inspection | Possible — tree is a transparent ADT | Possible — similar model |

## 10.9 Platform Declarations [Tested crates/cranelisp-frontend/src/module_extract.rs::test_platform_extracted]

```clojure
(platform name)
```

A `(platform name)` form declares which platform DLL provides IO operations for the program. It is **only valid in the entry module**. The `name` is a bare symbol identifying the platform (e.g., `stdio`, `test-capture`).

### 10.9.1 Scope [Tested crates/cranelisp-frontend/src/module_extract.rs::test_platform_extracted]

Platform declarations are entry-module-only:

- A `platform` form in any non-entry module is a compile-time error.
- Library and non-entry modules that need platform functions use `(import [platform.name [*]])` where `name` is the declared platform. The platform module is available once the entry module has declared it.
- Platform names are resolved via the platform DLL search order (§8.11.3).

### 10.9.2 Purpose [S10]

Platform declarations control which concrete implementations of IO operations are loaded. Each platform provides a set of functions with IO-returning types. Alternative platforms can substitute different implementations while preserving the same type signatures. User code that depends only on the type-level contract works with any conforming platform.

### 10.9.3 Syntax [S10]

The platform name is a bare symbol, not a string literal:

```clojure
(platform stdio)          ; correct — bare symbol
(platform "stdio")        ; ERROR — string literal not allowed
```

## 10.10 Platform ABI Contract [Tested tests/link::link_repeated_platform_adt_marshal_does_not_corrupt_heap]

Platform libraries provide IO operations via dynamically loaded shared libraries. The contract between platform libraries and the Cranelisp runtime is defined at the C ABI level.

### 10.10.1 Calling Convention [S10]

Platform functions use the C calling convention (`extern "C"`). All parameters and return values are `i64` at the ABI level. The interpretation of each `i64` depends on the Cranelisp type:

- `Int` -- the integer value directly
- `Bool` -- 0 for false, 1 for true
- `String` -- pointer to heap-allocated string (see [Section 12](12-runtime.md))
- `IO a` -- pointer to heap-allocated IO task tree node (Pure, Effect, or Bind)
- `Fn a b` -- pointer to the heap-allocated closure struct (runtime fn value; layout per `design/arch/CLAUDE.md` Decision 11). The platform MUST NOT cast this `i64` and invoke the closure's code pointer directly. The platform MUST invoke the closure only via a runtime-provided host callback (exposed through the `HostCallbacks` struct; see §10.10.3), which performs GOT-indirect dispatch so every invocation reaches the currently-defined code. If the platform retains the closure beyond the dynamic extent of the call (for example, storing it for later or asynchronous invocation), the platform MUST use runtime-provided `rc_inc`/`rc_dec` host callbacks (see [Section 12](12-runtime.md) for the RC header discipline) to keep the heap closure alive while retained and to release it when no longer retained. [S-future]

The `Fn a b` row is a **forward commitment**: no current platform accepts a fn-typed argument, so the rule is not yet exercised by any conforming implementation. It is recorded here to preserve the safety invariant established by `design/arch/CLAUDE.md` Decision 31 (JIT memory lifecycle) -- namely, that platform-held callbacks MUST remain valid across REPL redefinition, which requires GOT-indirect dispatch and runtime-managed lifetime rather than raw code-pointer capture. The concrete host-callback names and signatures will be added to §10.10.3 and the `HostCallbacks` struct when the first platform requires fn-typed arguments. Platforms MUST NOT anticipate those names; they become normative only once specified. [S-future]

### 10.10.2 IO Return Requirement [S10]

Every platform function MUST return an `IO` type — unconditionally, not only those that "appear to" perform side effects. The compiler cannot inspect foreign native code, so it cannot verify purity and MUST trust the declared signature; a platform function declared with a non-IO (pure) return type would be treated as pure by the type system — eligible for memoization, reordering, elision, and lenient/parallel sparking — while the foreign host performs arbitrary effects, which is unsound. Requiring `IO` ensures every foreign effect is tracked and sequenced in the type system. See §[8.9.3](08-modules.md#893-platform-modules) for the full rationale; the implementation rejects any platform function whose declared return type is not `IO _`.

### 10.10.3 Allocation Callback [S10]

Platform libraries receive an allocation callback from the host runtime. This callback is used to allocate Cranelisp heap values (such as IO task tree nodes and strings) using the runtime's allocator, ensuring proper memory management integration (reference counting).

### 10.10.4 Implementation-Defined Details [S10]

The specific mechanism for registering platform functions, the allocation callback interface, and the shared library discovery path are implementation-defined.

## 10.12 Automatic IO Scheduling [Tested tests/spec_10_io::resource_serial_same_token_serializes]

There is no `par-bind!` form in the language. Concurrent IO is automatic: the compiler MUST perform independence analysis on `bind!` chains and MUST insert `Par` nodes for commutative, data-independent effect pairs.

### 10.12.1 Semantics [Tested tests/spec_10_io::auto_io_independent_diff_token_parallelizes_e2e]

The compiler performs an independence analysis on each `bind!` chain. For a pair of bindings `(xi, ei)` and `(xj, ej)`:

- **Data independence**: `xi` is not free in `ej`, and `xj` is not free in `ei`.
- **Commutativity**: both `ei` and `ej` call a platform function whose manifest declares `SchedulingClass::Commutative`.

When both conditions hold, the compiler inserts a `Par` node. The trampoline MAY then execute the `Par` branches concurrently; the execution mechanism is implementation-internal and not prescribed (see §10.12.5 and §10.12.6). [S94]

Effects between Sequential bindings are always executed in source order. Effects between Commutative bindings MAY execute in any order. Correct programs MUST NOT depend on the relative ordering of effects within a set of Commutative bindings.

### 10.12.2 Platform Scheduling Classes [Tested crates/cranelisp-backend/src/compiler/control_flow.rs::sequential_let_emits_no_par_node]

Platform functions declare their scheduling class in the manifest. Users do not annotate effects directly.

| Class | Meaning | Examples |
|---|---|---|
| `Sequential` | Ordered relative to other calls to this function | `read-line`, `print` |
| `Commutative` | Freely reorderable; no shared state between calls | `http-get`, `time-now` |
| `ResourceSerial` | Parallel unless runtime resource tokens conflict | `file-read(fd)`, `log(handle, msg)` |

### 10.12.3 Examples [S11]

```clojure
;; Compiler parallelises: both http-get calls are Commutative + data-independent
(bind! [response1 (http-get "url1")
        response2 (http-get "url2")]
  (pure (process response1 response2)))

;; Compiler preserves order: read-line is Sequential
(bind! [line1 (read-line)
        line2 (read-line)]
  (pure (str-concat line1 line2)))
;; line1 is always the first line read, line2 the second
```

### 10.12.4 Runtime Resource Tokens [Tested tests/spec_10_io::resource_serial_same_token_serializes]

`ResourceSerial` platform functions set a runtime resource token on their `Effect` node (a non-zero i64 that uniquely identifies the resource they access). Within a `Par` group, the trampoline:

1. Groups `Effect` nodes by resource token.
2. Runs branches with `token=0` (unrestricted) each independently and concurrently (via whatever execution mechanism the implementation provides — see §10.12.5).
3. For each non-zero token group, runs all branches in that group sequentially as a single work item.

Branches in different token groups run concurrently; branches with the same non-zero token are serialised regardless of data independence, **and execute in source order** — the order their bindings appear in the `bind!` chain. Mutual exclusion alone is insufficient: same-resource effects are observable in their relative order (e.g. successive appends to one log file, or ordered writes to one file descriptor), so a same-token group preserves source order, not merely the property that its branches do not overlap. A conforming implementation MUST NOT reorder the effects within a single non-zero token group.

The serialisation in this subsection is the limiting case (one effect at a time) of the more general **resource capacity** of §10.12.4.1.

### 10.12.4.1 Resource Capacity — Token Pools [S95]

§10.12.4 describes the case in which a resource admits **one** effect at a time. A resource may instead admit several concurrently. The platform characterises each resource by a **capacity** *N* — the number of effects on that resource that may safely be in flight at once (the size of the resource's *token pool*). Capacity generalises the scheduling classes of §10.12.2: capacity 1 is `ResourceSerial`; an unrestricted (`token = 0`) effect has effectively unbounded capacity.

**Capacity attaches to the resource (the token), NOT to the effect.** A resource is identified by its non-zero token; its capacity is a property of that token, not of any single effect that uses it. This is load-bearing:

| # | Requirement | Status |
|---|---|---|
| 1 | Effects on **distinct** tokens have **independent** capacities — each token's pool is bounded only by its own capacity. | [S95] |
| 2 | Effects sharing **one** token share that resource's single pool — the total number in flight across **all** effects on the token MUST NOT exceed the token's capacity *N*, regardless of which distinct effects they are. (Canonical case: distinct effects — e.g. `query`, `execute`, `begin` — drawing from one connection pool of *N* connections; the sum in flight ≤ *N*.) | [S95] |
| 3 | Within a `Par` group, for a non-zero token of capacity *N*: up to *N* effects on that token MAY run concurrently; while *N* are in flight, any further effect on the token **parks** — it MUST NOT begin until one of the in-flight effects completes and frees a permit. The (N+1)th effect's deferral is observable as wall-clock latency (and, informatively, as a park/resume in the dev-facing strand stream of §10.12.6). | [S95] |
| 4 | Capacity 1 is exactly the `ResourceSerial` behaviour of §10.12.4: at most one effect on the token runs at a time, the rest serialise, **and they execute in source order** (exclusion *and* order). | [S95] |
| 5 | For capacity *N* ≥ 2 the up-to-*N* concurrently-admitted effects MAY overlap and MAY complete in any order; a correct program MUST NOT depend on their relative ordering. Source ordering is guaranteed only within a capacity-1 token (item 4). | [S95] |
| 6 | A `token = 0` (unrestricted) effect acquires no permit and is bounded by no pool (§10.12.4 step 2); this is unchanged. | [S95] |

Capacity is part of the platform's concurrency contract and is a **trust boundary**, continuous with the rest of §10.12: the compiler does not verify a declared capacity, exactly as it does not verify a `Commutative` claim or a `ResourceSerial` token. By declaring a resource's capacity *N*, the platform author asserts that up to *N* effects on that resource may run concurrently; the language takes this assertion on faith and does not check it. Exceeding *N* would be a correctness violation, which the capacity ceiling exists to prevent.

This description is **observational and mechanism-neutral** (consistent with §10.12.5): it constrains *what a program observes* — how many effects on a given token overlap, and that an effect beyond the token's capacity does not begin until a permit frees — not *how* the trampoline realises the pool. A conforming implementation MAY realise a capacity-*N* token with a counting semaphore of *N* permits keyed by the token, a bounded work queue, or purely sequential execution (which also conforms, admitting one effect at a time), provided the observable behaviour above holds. The strict within-token source ordering of §10.12.4 is a property of the capacity-1 case and, like that case, MUST be carried deliberately: a bounded pool of permits gives *exclusion* (an *N*-bound on concurrency) but not *order*, so a capacity-1 token preserves source order while a capacity-*N* token (item 5) imposes none.

Capacity is the platform-asserted *ceiling*. A separate, program-chosen in-flight throttle — the **degree** — composes with it; see §10.12.4.2.

### 10.12.4.2 Admission Degree — Program-Chosen Throttle [S96]

§10.12.4.1 specifies **capacity**: the platform-asserted ceiling on how many effects a resource may *safely* sustain. A program may additionally impose its own, stricter, in-flight limit — the **degree** — for reasons of its own: bounding memory, ensuring fairness across requests, or being polite to a remote service. Capacity and degree are different concepts owned by different parties:

| Aspect | capacity (§10.12.4.1) | degree |
|---|---|---|
| Asserted by | the **platform** | the **program** |
| Attaches to | the **resource** (the token) | the program's policy (a token, or globally) |
| Concern | **correctness** — exceeding it is unsafe (a trust boundary) | **policy** — memory / fairness / politeness; never a safety claim |
| Effect of violating | undefined / unsafe behaviour (the ceiling exists to prevent it) | none possible — over-degree work simply parks |

Requirements:

| # | Requirement | Status |
|---|---|---|
| 1 | When a program sets a degree *D* on a resource of capacity *N*, the effective in-flight limit on that token is `min(N, D)`. At most `min(N, D)` effects on the token MAY be in flight; a further effect **parks** until one frees — the same observable park as the (N+1)th-parks of §10.12.4.1 (wall-clock latency / backpressure), not an error. | [S96] |
| 2 | A degree set above the resource's capacity has no additional effect: capacity still bounds (`min(N, D) = N`). Degree can only *tighten* the limit, never loosen it past the platform-asserted ceiling. | [S96] |
| 3 | A program MAY also set a **global** degree bounding the total number of in-flight **detached strands** (§10.12.7) across all tokens. The accept loop of a server emits launched effects unboundedly (§4 of the model); this global bound is what keeps the fan-out's memory bounded — the over-bound launch parks until an in-flight detached strand completes. | [S96] |
| 4 | Over-degree parking NEVER drops or fails work; it only **defers** it. Backpressure is observable as latency, not as a lost effect or an error result. | [S96] |

Degree is **policy, not a trust boundary**: unlike a capacity claim (which the language takes on faith and whose violation is unsafe), a degree is merely a self-imposed throttle and can never be unsound — at worst it slows the program down. The means by which a program selects a degree (a deployment- or runtime-configuration value) is **implementation-defined**; degree is **not** a language form. This subsection constrains only what a program observes when a degree is in force — that at most `min(capacity, degree)` effects of a kind are in flight and the rest park — not how the runtime realises the throttle.

### 10.12.5 Runtime Mechanism [S11]

The compiler inserts a `Par` node (internal IO constructor, tag=3) for parallelisable pairs. The trampoline recognises `Par` nodes and MAY execute their branches concurrently, subject to resource token serialisation; results are collected and passed to the continuation. **The concurrency mechanism is implementation-internal and not prescribed** — consistent with the non-prescriptive runtime stance of [§12.1](12-runtime.md#121-value-representation). A conforming implementation MAY use a worker thread pool, a single-threaded reactor on which effects that wait (for example on I/O readiness) suspend and resume so that independent waits overlap, any combination of the two, or purely sequential execution (which also conforms — see [§12.4.3](12-runtime.md#1243-lenient-evaluation)). Whatever the mechanism, observable behaviour MUST satisfy §10.12.1–§10.12.4 and remain observationally identical to sequential left-to-right execution (§10.12.6, [§12.4.3](12-runtime.md#1243-lenient-evaluation)). The current implementation uses two mechanisms — a rayon worker pool for CPU/blocking work and a host-owned reactor on which poll-shape effects suspend and resume — described in `design/arch/effect-concurrency.md`. [S94]

### 10.12.6 Execution Substrate and Slice Delivery (informative) [S93]

> This subsection is **informative**: it records the disposition of the
> concurrency model's execution substrate. It introduces **no new user-visible
> language surface** and imposes no requirement beyond those already stated in
> §10.12.1–§10.12.5 and [§12.4.3](12-runtime.md#1243-lenient-evaluation).

The automatic scheduling of §10.12 is realised by an **execution substrate** — a
host-owned reactor that may overlap independent effects, and that may run
same-token effects under bounded resource pools — being delivered incrementally
("in slices"). Three facts fix what this means for the language:

1. **The substrate changes execution, not extraction.** The independence and
   token analysis of §10.12.1 and §10.12.4 stand verbatim. The substrate only
   changes *how* the extracted-concurrent work is run, never *which* work is
   eligible. Its results are **observationally identical to sequential
   left-to-right execution** under the equivalence already guaranteed by
   §12.4.3 (and the within-token source ordering pinned in §10.12.4). A program
   cannot distinguish the substrate from a conforming sequential implementation.

2. **The substrate, the per-effect concurrency descriptor (a generalisation of
   the §10.12.2 scheduling classes), and the strand-correlated observability
   event stream are implementation- and tooling-facing — not language features.**
   They are not invokable from cranelisp source, carry no in-language type, and
   produce no value a program can observe. In particular the **strand identity**
   (the correlation id threaded through the substrate for debugging and tracing)
   is a **dev/observability concern only**; it is not a queryable language value
   at this stage. It surfaces, if at all, through REPL/dev-facing diagnostic
   sinks (a sibling of [`trace`](04-expressions.md#412-trace-expression) and
   `io_trace`), which are outside the normative language surface.

3. **The explicit control surface is now fully specified.** **Launch-and-continue
   (un-joined) effects and the per-effect-kind supervisor policy** are specified
   in §10.12.7 (launch-and-continue) and
   [§12.7.9](12-runtime.md#1279-supervised-detached-strands) (supervisor),
   together with the program-chosen admission **degree** of §10.12.4.2. The
   typed control-combinator layer — `race` / `select`, a derived `timeout`, and
   the structured cancellation underneath them — is specified in §10.12.8
   (combinators), §10.12.9 (cancellation), and §10.12.10 (the reference control
   patterns: graceful shutdown, cancel-on-disconnect, per-request timeout), with
   its typing and runtime semantics in
   [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation).
   The control surface — like a detached strand — is the **explicit-control**
   half of the model and is deliberately outside the §10.12.1–§10.12.5
   sequential-equivalence guarantee (it abandons effects by design); the inferred
   half remains observationally identical to sequential execution.

### 10.12.7 Launch-and-Continue (Detached Effects) [S96]

The automatic scheduling described so far concerns effects whose completion the continuation **awaits** — the structured fork-join of [§12.4.3](12-runtime.md#1243-lenient-evaluation), in which every branch joins before the enclosing expression returns and a worker fault ferries back to that join. An effect may instead be **launched and not joined**: run concurrently with the continuation, which proceeds **without awaiting it**. This is **launch-and-continue** — the mechanism by which a server fans out request handlers with **no `spawn`** in the source.

**Eligibility.** An effect is eligible to be launched-and-continued when **both**:

1. its **result is discarded** — it occupies a non-final statement position whose bound value is unused (canonically an `IO Unit` effect ahead of the continuation in a `do` / `bind!` chain), so no later computation can observe its result; and
2. its **resource tokens are disjoint** from the continuation's effects (§10.12.4), so it cannot conflict with any subsequent effect.

In `(do (handle-conn conn) (serve listener))`, `handle-conn` returns `IO Unit` (its result is unused) over a per-connection token disjoint from `serve` — it is eligible. `serve` recurses to accept the next connection **without waiting** for `handle-conn` to complete, and the accept loop fans out automatically. No annotation appears in the handler.

**Observable contract.** When an eligible effect is launched as a **detached strand**:

| # | Requirement | Status |
|---|---|---|
| 1 | The detached strand runs **concurrently** with the continuation; the continuation MUST NOT block on its completion. | [S96] |
| 2 | The launching strand **never observes** the detached effect's **result** — guaranteed trivially by eligibility (the result is discarded). | [S96] |
| 3 | The launching strand **never observes** the detached effect's **fault**. A runtime panic ([§12.7.2](12-runtime.md#1272-runtime-panics)) raised in a detached strand MUST NOT propagate into, or abort, the launching strand; it is contained by the supervisor ([§12.7.9](12-runtime.md#1279-supervised-detached-strands)). This is the **opposite** of the structured fork-join (§10.12.4, §12.4.3), where a worker fault DOES ferry to the join and the **first** such error aborts the enclosing expression. The first-error-wins propagation of §12.4.3 applies **only to structured joins**, never to a detached strand. | [S96] |
| 4 | The in-flight count of detached strands is bounded by the admission **degree** (§10.12.4.2 item 3), not by source structure: the accept loop emits launches unboundedly and the global degree throttles execution (over-bound launches park). | [S96] |

**Relationship to the observational-equivalence guarantee.** The auto-IO scheduling of §10.12.1–§10.12.5 is guaranteed observationally identical to sequential left-to-right execution (§10.12.6, §12.4.3). **A detached strand is the deliberate exception — it is NOT part of that guarantee.** Because its result is discarded by eligibility, the *value the program computes* is unchanged whether the effect runs detached or inline; what a detached strand changes is (a) **timing** — it overlaps the continuation rather than completing before it — and (b) **fault containment** — its panic is handled by policy ([§12.7.9](12-runtime.md#1279-supervised-detached-strands)) rather than aborting the program. (a) and (b) are the **explicit-control** half of the model: the program gains a server that survives a failing request, at the cost of stepping outside the sequential-equivalence promise that covers the inferred half. Whether a given eligible effect is in fact run detached, inline, or on a worker is implementation-determined and unobservable *at the value level*; the detached-mode contract above governs only its timing and its fault behaviour. The TCO interaction is pinned in [§12.5](12-runtime.md#125-tail-call-optimization).

### 10.12.8 Structured Control Combinators — `race` / `select` / `timeout` [S96]

The scheduling of §10.12.1–§10.12.7 is **inferred**: the compiler extracts concurrency from dataflow independence, and a program neither requests nor observes it beyond its timing. This subsection specifies the **explicit-control** half — a small set of in-language combinators by which a program **explicitly** runs effects against one another and bounds them in time. They are the irreducible vocabulary for an uncooperative I/O boundary (a slow peer, a client that disconnects, a request that must not outlive its deadline) — the cases the inferred half cannot reach because they require the program to choose what to *abandon*.

The combinators are **ordinary typed functions**, not special forms and not platform effects: each takes `IO` value(s) and **constructs a new `IO` value** describing the concurrent composition (the same mechanism class as the compiler-inserted `Par` node of §10.12.5). They are pure with respect to construction — building the `IO` runs nothing — and the composed effect runs only when the resulting `IO` is itself sequenced into the program's effect (via `bind!` / `do`) and reaches the trampoline. Their typing and runtime semantics are pinned in [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation); this subsection states the **observable contract**.

| Combinator | Indicative type | Observable result |
|---|---|---|
| `race` | `IO a -> IO a -> IO a` | Runs both effects concurrently; completes with the value of the **first to complete**. The other (the **loser**) is **cancelled** (§10.12.9). |
| `select` | `Vec (IO a) -> IO a` | The *n*-ary generalisation of `race` over a homogeneous **vector**: runs all effects concurrently, completes with the value of the first to complete; **all other branches are cancelled** (§10.12.9). `select [a, b]` is observationally equivalent to `race a b` (the `[..]` literal is a `Vec`, not a `List`). The empty vector `select []` has no branch that can win — it MUST raise a runtime error (see "Empty `select`" below), not return a value. |
| `timeout` | `Int -> IO a -> IO (Option a)` | Runs the effect against a timer of duration *d* **milliseconds** (see "Duration unit" below). Completes with `(Some v)` if the effect completes first (value *v*), or `None` if the timer fires first — in which case the effect is **cancelled** (§10.12.9). Derived: `timeout d io` ≡ `race` of `io` against a `(sleep d)` timer (the stdlib derivation; see [§11](11-stdlib.md)). |

**Observable contract.**

| # | Requirement | Status |
|---|---|---|
| 1 | `race`/`select` complete with the value of **exactly one** branch — the **winner**, the first branch to complete. Exactly one branch's value is returned; every other branch is cancelled and its value is **never** returned or observed. | [S96] |
| 2 | **Determinism of the winner.** The winner is the branch that **completes first** in wall-clock time. When two or more branches have completed before the runtime observes either, **which of the completed branches wins is unspecified** (it is NOT guaranteed to be the source-order-first branch). This is the same honest non-determinism as the `Par` first-error caveat (§10.12.1, [§12.4.3](12-runtime.md#1243-lenient-evaluation)): a program MUST NOT depend on which of several simultaneously-ready branches is chosen. A program that needs a deterministic tie-break MUST encode it (e.g., order-sensitive branches that cannot complete simultaneously). | [S96] |
| 3 | **`select`/`race` return only the winner's value, not its index.** The combinators do not report *which* branch won. A program that must distinguish the winner encodes the discriminant in each branch's result type — e.g., each branch returns a tagged value `(map Left a)` / `(map Right b)` — so the returned value itself identifies the source. (This keeps the combinator set minimal; an index-returning variant is derivable and not primitive.) | [S96] |
| 4 | **Losers are cancelled, not merely ignored.** A losing branch is not left running to completion with its result discarded; it is **cancelled** per §10.12.9 — its in-flight effect does not run to its completion side-effect, and its resources are released. This is the load-bearing difference from launch-and-continue (§10.12.7), where the detached effect runs to completion unobserved. | [S96] |
| 5 | `timeout` returns `None` **only** when the timer fired before the effect completed; on `None` the wrapped effect is cancelled (§10.12.9). `timeout` returning `(Some v)` guarantees the effect completed normally and the timer was cancelled. The two outcomes are mutually exclusive. | [S96] |

**Duration unit.** The language has no dedicated `Duration` type; a duration is an ordinary `Int`. Both `sleep`'s argument and `timeout`'s deadline *d* are an `Int` count of **milliseconds**. `(sleep 100)` parks for ≈100 ms and resolves with `0`; `(timeout 100 io)` bounds `io` by ≈100 ms. The leaf timer is `sleep : Int -> IO Int` — an `IO` effect that parks for the given number of milliseconds and resumes with `0`. This unit is normative: a conforming implementation MUST interpret the argument as milliseconds. [Tested tests/concurrency_sleep.rs::sleep_parks_for_duration_then_resumes_and_continues, tests/concurrency_sleep.rs::sleep_links_and_runs_through_link_mode]

**Empty `select`.** `(select [])` over an empty vector has no branch that can win and no value to return. It MUST raise a runtime error (§[12.7.2](12-runtime.md#1272-runtime-panics)) rather than return a value. Returning a synthesised value is non-conforming: at a heap-typed `a` an `Int`-`0` placeholder is an unsound null pointer, and downstream RC/field reads on it are undefined behaviour; a "never completes" hang is also non-conforming (a guaranteed deadlock is worse than a clean fault). **The raise is at effect-run time, and is therefore fatal — NOT catchable.** The select node's emptiness is detected when the trampoline *runs* the node, which is **outside** any `catch-runtime-error` construction bracket (§[A.3](appendix-a-builtins.md) catchability boundary; §[12.7.2](12-runtime.md#1272-runtime-panics) "the bracket is temporal"). Wrapping the select in a thunk does not help: it only defers the raise past the bracket. An empty `select` is thus a fatal programming error — process-terminating in batch, expression-aborting in the REPL (§[12.7.4](12-runtime.md#1274-repl-vs-batch-error-behavior)) — that a program can neither catch nor depend on for a value. This is the honest general answer for **every** run-time effect error, not a select special case (it generalises rather than special-casing literal-empty vs runtime-empty `select`). [S98 — /spec ruling (FIXME 0487), resolution (a) fatal-runtime-error; raise enforced in the empty-`select` mechanism (S97, `io.rs` — backend-emitted runtime per FIXME 0486); the catchability guard `tests/concurrency_v9_select::empty_select_caught_by_catch_runtime_error` (4.2) retires as wrong-premise → /qa]

**Relationship to the observational-equivalence guarantee.** Like a detached strand (§10.12.7), the control combinators are the **explicit-control** half of the model and are **NOT** part of the §10.12.1–§10.12.5 sequential-equivalence guarantee. That guarantee covers the *inferred* half, where every effect runs to completion and the only freedom is ordering/overlap of independent effects. A combinator deliberately **abandons** an effect (the loser, the timed-out work): the set of completion side-effects a program produces is **not** the same as running every branch to completion sequentially — which is exactly the point, and is the program's explicit choice. The combinators' value-level result is well-defined (item 1); what steps outside sequential-equivalence is the cancellation of the abandoned branches (§10.12.9). See [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation).

### 10.12.9 Structured Cancellation [S96]

Cancellation is the load-bearing semantics underneath §10.12.8: when a `race`/`select` loser, a `timeout`'d effect, or an effect whose enclosing scope exits is **cancelled**, what a program may and may not observe of it is fixed. Cancellation is **not** a standalone user combinator — there is no `cancel` function and no user-installable handler. It is the *consequence* of an effect ceasing to be awaited (losing a race, a timer firing, a scope unwinding); the program expresses cancellation only by the structure of the combinators above.

**Observable contract.** When an in-flight effect is cancelled:

| # | Requirement | Status |
|---|---|---|
| 1 | **Resources release.** Every resource the cancelled effect held MUST be released: a resource-capacity **permit** it acquired (§10.12.4.1) is returned to its token pool, and any reactor interest it registered (an fd-readiness wait, a timer) is deregistered. Releasing the permit is observable: a permit freed by a cancelled effect MUST become available to an effect parked on that token (the (N+1)th of §10.12.4.1 can then proceed). A program MUST NOT be able to exhaust a token pool by cancelling effects on it. | [S96] |
| 2 | **No completion side-effect.** A cancelled effect MUST NOT produce its **completion** side-effect: the value it would have computed is never returned, and any effect it had not yet performed at the cancellation point does not occur. Side-effects it had **already** performed before cancellation are **not** undone (cancellation is not a transaction/rollback) — the contract bounds *future* observation, not the past. What a program can observe of a cancelled effect is therefore exactly: whatever it had already done before the cancellation point, and nothing after. | [S96] |
| 3 | **Cancellation is not a fault.** A cancelled effect does not raise a runtime panic (§12.7.2) into the cancelling context, and it is not routed to the supervisor (§12.7.9). The winner's value (or `None`, for `timeout`) is the only result the combinator yields; cancellation of the losers is silent at the value level (it surfaces only through the dev-facing observability stream of §10.12.6 — a `cancellation` event). | [S96] |
| 4 | **Cleanup runs.** Cancellation releases the cancelled computation's live heap values through ordinary drop glue (§12.7) as its strand is torn down; reference counts are decremented and freed exactly as on normal completion. Cancellation MUST NOT leak the cancelled effect's resources (this is items 1 + 4 together: the permit, the reactor interest, and the heap). | [S96] |

This contract is **observational and mechanism-neutral**: it constrains what a program observes of a cancelled effect — that its resources free, that its completion side-effect does not occur, that it raises no fault — not how the runtime tears the effect down. A conforming implementation realises cancellation by dropping the in-flight future (releasing its acquired permit and deregistering its reactor interest as part of that drop); see [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation) and `design/arch/effect-concurrency.md` §9. The permit-release and reactor-interest-deregistration on cancellation are the runtime obligations this observable surface rests on.

### 10.12.10 Reference Control Patterns — Graceful Shutdown and Cancel-on-Disconnect [S96]

The combinators (§10.12.8) and cancellation (§10.12.9), composed with launch-and-continue (§10.12.7) and the supervisor (§12.7.9), give the control patterns that let a long-running server survive an open-internet environment. These are **derived patterns**, not new primitives; this subsection pins their observable contract because they are the user-facing reason the control half is a committed deliverable (§1 of `design/arch/effect-concurrency.md`).

| Pattern | Built from | Observable contract | Status |
|---|---|---|---|
| **Per-request timeout** | `timeout d handler` | A request handler that does not complete within *d* is cancelled (§10.12.9): its permit and reactor interest free, its remaining effect does not occur, and the request receives a timeout outcome (`None`) rather than hanging indefinitely. The server continues serving other requests. | [S96] |
| **Cancel-on-disconnect** | `race handler (await-disconnect conn)` | A handler racing against the connection's disconnect-detection effect is **cancelled** when the client disconnects first: the now-pointless work stops (§10.12.9), freeing its permit so a live request may use it. A disconnected client's handler MUST NOT continue to consume a resource permit to completion. | [S96] |
| **Graceful shutdown** | cancellation of outstanding detached strands (§10.12.7) on a shutdown signal | On shutdown, the outstanding detached strands (the in-flight launched handlers) are cancelled (§10.12.9): each releases its resources and stops producing further effects; the program then terminates with its in-flight work torn down cleanly rather than abandoned mid-effect or forced to run to completion. | [S96] |

The observable invariant common to all three: **abandoned work releases its resources promptly and stops producing effects** (§10.12.9), so a server's resource pools (§10.12.4.1) are not pinned by work no one is waiting for. The mechanisms by which a program detects a disconnect or receives a shutdown signal are platform effects (ordinary `IO`, §10.10) and are implementation-/platform-defined; this subsection constrains only the cancellation observable that results from composing them with the combinators.
