# 0025 — Compiled code lives on `ModuleEntry::Def.code` as a `#[serde(skip)]` field; cache stores both `.meta.json` and `.o`, cache-hit LOADS the `.o`, does not re-codegen

Per-function compiled code (`Code { jit: Arc<Jit>, ptr: *const u8 }` for fresh-build; `Code::Linker { linker: Arc<Linker>, ptr: *const u8 }` for cache-hit per Decision 35) lives on the `ModuleEntry::Def.code: Option<Code>` field, not in a separate `CodegenProduct` DashMap. The field is `#[serde(skip)]`: runtime state only. This is the `pipeline-v4.md` §9.1 / §9.4 target shape — not a stepping stone.

**Cache shape (corrected Sprint 58 Wave 2).** The cache stores BOTH `.meta.json` (the serialised `SymbolTable<(), ()>` — types, schemes, GOT slot layout, AST bodies, structural decls, `schema_version`) AND `.o` (the per-module `ObjectModule` Cranelift output — native code + the `.o` data section GOT defined as `Linkage::Export` per Decision 23 + Decision 36). Cache-hit LOADS the `.o` via `Linker::load_object`, looks up function symbols by their bare names, and writes the resolved code addresses into the SymbolTable GOT slots; it does NOT re-run codegen. Earlier framing of this decision said "regenerated from `ast` on cache-hit load" — that wording was wrong. Codegen runs only on fresh build (no cached `.o`); on cache-hit, the `.o` IS the regenerated output, and the cached symbol table's `got_slot` layout (pinned at typecheck time) tells the loader which slots to populate. The two paths are symmetric in *what ends up in memory*: SymbolTable populated with types/AST; SymbolTable GOT populated with code pointers reachable from native code. They differ only in HOW each step lands (typecheck vs deserialise; codegen vs `Linker::load_object`). The generics form `SymbolTable<C: CodeStore, L: LinkerStore>` that appears in `pipeline-v4.md` §9.1 was initially deferred per `pipeline-v4-roadmap.md:198`: `#[serde(skip)]` on a concrete `Code` was deemed sufficient for Phase 3+, and introducing generics would touch every `SymbolTable` use-site without then-visible behavioural payoff. Phase 5 (Sprint 58 Wave 3) activated the generics; see the **Update** paragraph below. The `Code` type lives in the integration layer at `src/code.rs` (per Decision 35 Layer 2 Option B). Rejected alternatives: (a) keep `CodegenProduct` as a "fast path" for REPL eval (premature perf workaround — see memory/feedback_no_premature_perf.md); (b) **(rescheduled, now landed)** eagerly introduce `SymbolTable<C, L>` generics before Phase 3. Originally rejected as a 182-call-site change for "API cleanliness only, no behavioural payoff" — correct on the evidence then available. Decision 31 subsequently identified the generics as the DAG-compatible mechanism for placing `Arc<Jit>` directly on `ModuleEntry::Def.code`, which is what enables per-redefinition JIT reclaim (Decision 31 Scenario 2); the "no behavioural payoff" rationale no longer holds. The generics activation landed in Sprint 58 Wave 3 (Step 5c, gap G12), alongside the structural-declaration and cache-serialisation work. Phase 5 was the earliest phase in which the structural foundation was in place AND generics delivered concrete behaviour rather than abstract cleanliness; deferral remained correct through Phase 3–4. The **Update** paragraph below records the landing. Canonical location: `crates/cranelisp-types/src/module.rs` `ModuleEntry::Def`; owner of `Code`: `/int`. Rationale: Principle 11 (single store on `SymbolTable`) + Principle 8 (final shape, not an interim) + Principle 7 (one code location per symbol — no DashMap-vs-entry divergence).

**Update (Sprint 58 Wave 3 close — rescheduled alternative now actioned).** The rescheduled-alternative `SymbolTable<C, L>` generics activation is now landed (commits `03b218f` Wave 3a + 3b, `d22e044` Wave 3c, `d348bca` Wave 3d).
