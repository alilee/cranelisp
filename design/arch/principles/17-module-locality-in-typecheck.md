# Principle 17 — Module locality in typecheck

**Statement.** Typecheck never iterates the universe of modules to resolve a name, a type, an impl, or a method. Cross-module access happens only via fully-qualified references whose target module is named, or via per-symbol point-to-point **chain-follow** along `ModuleEntry::Import` / `ModuleEntry::Reexport` bindings back to the symbol's defining module. Bulk introspection (`all_type_defs`, `all_macros`, etc.) operates on the current module only; broader views are composed at the session/REPL layer, not from inside a typecheck pass.

**Navigation primitive is point-to-point chain-follow.** Cross-module lookups proceed by following a per-symbol `ModuleEntry::Import` or `ModuleEntry::Reexport` binding back to its defining module, one edge at a time, terminating when the defining module is reached. This is per-name, per-edge — not per-graph. No cycle detection, no visited-set, no enumeration of an import closure is required: each chain-follow is a finite recursion along `source.module` references, terminating at a non-`Import`/non-`Reexport` entry (the canonical definition).

**Short-name resolution algorithm.** A short name `foo` resolves by lookup in the current module's `SymbolTable` only. If `foo` is absent, the lookup fails. There is no fallback to any other module — no root module, no implicit primitives sweep, no closure walk, no graph traversal. Universally-feeling symbols (`Int`, `+`, `not`) are reachable because the prelude (per spec §8.8.1) injects per-symbol `ModuleEntry::Import` bindings into user modules; the bindings carry the reach, not the resolver. Special forms (`if`, `let`, `match`, ...) never enter resolution — they are recognized by the parser/expander and lowered into AST nodes before any name lookup runs. The "root module" at path `""` is a notional concept for reasoning about universal symbols; no `SymbolTable` instance exists at that path.

**Closure walks are forbidden.** Graph traversal over `imports` + per-symbol `Import` / `Reexport` entries — collecting the "set of all modules transitively reachable from M" with cycle detection and visited-set bookkeeping — is NOT a legitimate navigation pattern in typecheck. The "effective import set" of a module is not computed *as a set*; reachability questions are answered point-to-point per query, by chain-following the specific symbol whose reachability is being asked about. A function with the shape `transitive_import_closure(module) → Set<ModuleFullPath>` is a defect in this principle and must be replaced with per-name chain-follow at every call site.

**Synthetic modules have empty `imports` and `exports` as an invariant.** `primitives`, `macros`, and any future synthetic compiler-seeded modules have no source forms; `imports` and `exports` are empty `Vec`s by construction. Anything in such a module that references types or symbols from another synthetic module MUST construct those references fully-qualified at registration time (`Type::ADT(macros_fqtn("SList"), …)`), not via short-name resolution that would require import-graph reachability. Defensive injections of synthetic glob imports (e.g., `(import [macros [*]])` into `primitives.imports`) are workarounds for a path that should not exist — the FQ-at-registration discipline is the canonical path.

**Rationale.** A "search every module for a short name" pattern is module-system-shaped wrong: the language's visibility rules already decide which names are reachable from the current module, and an unbounded scan disregards them. Concretely, the prototype carried 40+ direct `self.modules.X` accesses across `crates/cranelisp-typecheck/src/{checker,infer,traits,builtins}.rs` (Sprint 66 Wave 3a /dev third re-attempt audit, 2026-05-12) — short-name lookups iterating every loaded module, `find_impl_for_type` scanning the whole module set, `all_methods_of_type` iterating across modules, mutating writes landing in foreign modules. Each of these violates the visibility rule the spec already states (`spec/05-definitions.md §5.11`, `spec/08-modules.md §8.3`); each blurs the cluster-atomic surface (Decision 44) by introducing reads and writes that aren't governed by the orchestrator's `ClusterContext`. The remediation is to encode the visibility rule in the access pattern: a name is reachable from the current module iff it is local, imported, or imported transitively — and the typechecker walks that bounded set rather than the universe.

**Consequence.** Typecheck has four legitimate access-pattern shapes; every cross-module lookup must fit one of them:

1. **Unqualified short-name lookup** — `view.lookup(name)` against the current module's view (staging ∪ live, per Decision 44). If the entry is `ModuleEntry::Import { source: FQSymbol }` or `ModuleEntry::Reexport { source: FQSymbol }`, chain-follow `source.module` one edge at a time until a canonical (non-Import / non-Reexport) entry is reached. Never iterate `self.modules`.
2. **Qualified (FQ) lookup** — `symbol_tables.get(&fq.module).get(&fq.symbol)`. Direct, single module; the path is named.
3. **Impl resolution via trait-home chain-follow** — given a `(Trait, Type)` pair, chain-follow the trait reference back to its defining module (per shape 1) and probe that one module's table for the synthetic `impl$FQTypeName$FQTraitName` key (Decision 0045). Bounded by chain depth (typically ≤ 3), not by the import set, not by the universe. The impl is reachable from N iff the trait is reachable from N — encoded structurally by the chain-follow's termination at the trait's home.
4. **Bulk introspection** — current-module-only scan. Accumulating "everything reachable from the current module" is the orchestrator's job (session / REPL layer composes per-module slices), not the inside of `check_forms`.

Mutating writes are governed by Decision 44: every write goes through `ctx.current_symbol_table_mut()` (i.e., into staging or live for the orchestrator-selected target module). A typecheck pass MUST NOT mutate a foreign module's table directly. `TraitImpl` entries are written to the **trait's defining module** (Decision 0045) — the orchestrator selects the target table by chain-following the trait reference at write time, identically to the read side. Impl placement is therefore consistent with this principle by construction: the same chain-follow primitive serves both sides.

This principle is the structural prerequisite for Decision 44's cluster-atomic shape. The `ClusterContext` accessor surgery only buys atomicity if every read and write actually flows through it; an orphaned `self.modules.X` pierce does the wrong thing in cluster mode (it would read live during a cluster, ignoring staging) and silently weakens the live-table invariant. Compliance with this principle and compliance with Decision 44 are the same property viewed from two angles.
