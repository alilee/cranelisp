# Architectural Principles

The criteria `/arch` applies to every design decision and the standard against which sprint scope is reviewed. Maintained, not duplicated — when these principles are cited elsewhere (skill defs, design docs, reviews) they are cited by name; this file is the single canonical home.

The principles below were derived from the prototype's complexity analysis (59 audit findings across 4 modules) and refined as the reimplementation has progressed. Sprint citations record the originating context where one is recorded; principles 11–13 are Sprint 26 additions surfaced by the dual-pipeline defect.

Authoring and revision are part of `/arch`'s role. Principles evolve at sprint close (Phase 7 review per the methodology) — never mid-sprint, to avoid reactive rule-making. Revisions cite the sprint that motivated the change and commit before sprint archive.

- [Principle 24](principles/24-resolve-once.md) — Resolve once — a semantic identity is derived by exactly ONE keyed-lookup CHAIN at exactly ONE pipeline stage and crosses stage boundaries as a resolved FQ value; downstream stages do keyed reads and hard-fail on miss, never re-derive. Resolution is a chain of keyed lookups (scope precedence + explicit import/re-export pointers + prelude-fallback-once), never a search: NO ambient scan derives a compile-necessary identity at ANY stage — there is no valid search for identity. Carve-outs: complete-set enumeration (order-independent; failure mode incompleteness, not divergence; dispatch selection is this shape) and the human-facing `/search` scan, the one sanctioned genuine scan (S110 — motivating context: FIXME 0583's backend resolver, the "two resolvers, one name" mirror class 3× in S109; instances unified: 0583/§10-DC-11/0590/0585/R-2; user directive S109 P5; authored S110 Phase 3, strengthened compiler-wide S110 Phase 7, **ratified by the user at S110 Phase-7 close, 2026-07-16**, with the strengthened wording). **Corollary "resolution products travel typed" (S114 Phase 3, user-directed 2026-07-19 — FIXME 0653):** a resolution product travels as its typed value past the seam (bare name past the seam = defect marker); body-scans use the AST name only as a trigger for a keyed read of the recorded verdict; the local/global dichotomy is enforced IN THE TYPE — the closed `VarRef`/`ApplyRef` sums, "unresolved" has no constructor, sweeps are migration aids never the mechanism (register confirmation at S114 Phase-7 close)
- [Principle 25](principles/25-narrowing-carries-its-check.md) — Narrowing carries its check — a safety elision is defined against, and checkable against, its conservative fallback. (1) Conservative-at-⊤ is the reference semantics: an optimized artifact is correct by definition iff observationally equivalent (behavior + heap balance) to the conservative lowering, and an elision without a reachable conservative fallback is architecturally inadmissible. (2) Widening is free; every narrowing names its justification and its check at the strongest applicable tier of the assertion ladder (`safety-invariants.md` §2) — green example suites and adversarial review are discovery, not checks. (3) A foundational safety invariant is asserted at its seam, not merely tested (register: `safety-invariants.md` §4). The enforcement arm of monotone soundness — P18 applied to dynamic judgments, P20 extended from data shape to analysis claims (S111 — motivating context: the S111 memory-safety ledger — 0641 false-`Fresh` family, 0633/0640 glue-keying collisions, CS-4 wrong-accepts, 0604's unlocatable phantom write — found only by adversarial review/incident, closed only where an assertion mechanism landed (CS-2 seam asserts, CS-1.2 decoder witness); framed `safety-invariants.md` §5, **ratified by the user at S111 Phase-7 close, 2026-07-18, as a single principle** — the two-way split was offered and declined)
- [Principle 26](principles/26-record-from-settled-state.md) — Record from settled state — a resolution (dispatch target, mangled name, recorded type, pending-work entry) is recorded only from state whose owning pass has finalised it: every resolution carrier has an owning pass and a temporal window — derived values recorded at-or-after their inputs' settlement point, requests recorded only while the draining pass is still ahead. Admissible shapes: DEFER (record the site; derive once at settlement as a pure function of finalised state) or derive-on-demand post-settlement; the provisional-record-plus-repair shape is inadmissible (a forgotten carrier dangles silently; a later-added carrier is missed by construction — P22's published-pointer hazard in temporal form). Acid test = P24's applied to time: does the recorded value depend on where within the pass the record was made? (S112 — motivating context: the W2/W2.1 recurring class "resolution recorded against state a later pass owns", 3 instances at the typecheck multi-sig seam — B1 mid-drain `SigDispatch` dangling a removed `$Var` template (fixed `b5fa3f14`), I1 pending entry pushed after the drain (fixed `b5fa3f14`), R1 cross-arity variant an S113 attributed carry; two of three closed by the ONE §11.3.2 deferral mechanism in `design/typecheck/monomorphisation.md`; two further S112 confirmations — the eval.rs surface-syntax re-derivation display defect (fixed `40f19693`) and R2 carrier-never-derived-for-minted-mono-bodies (S113); authored S112 W3 per the escalate-on-3rd-instance rule, **ratified by the user at S112 Phase-7 close, 2026-07-18**)
