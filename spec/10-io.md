# 10. IO Model

This section defines how Cranelisp tracks and performs side effects. IO in Cranelisp is tracked by an opaque built-in type representing deferred computations. The type system distinguishes IO results from non-IO results; calling a function performs no effect, including when it returns IO (§3.2.3).

## 10.1 IO Type [Tested+Neg tests/opaque_io::s125_io1_pure_dotted_neg_run, tests/opaque_io::s125_io1_pure_imported_neg_run, tests/opaque_io::s125_io1_pure_pattern_neg_run, tests/opaque_io::s125_io1_effect_pattern_neg_run, tests/opaque_io::s125_io1_bind_dotted_neg_run, tests/spec_10_io::s124_io_opaque_pure_constructor_refused_run, tests/spec_10_io::s124_bind_spelling_outcomes_agree_run, tests/spec_10_io::s124_io_match_not_runtime_match_failed_run — every spelling of `Pure`, `Effect` and `Bind` refused in an expression and a pattern, in every mode (21 IO-1 cells); controls tests/opaque_io::s125_io1_user_pure_dotted_control, tests/opaque_io::s125_io1_user_pure_pattern_control. A match with no constructor arm, including on `IO`, is refused by §6.1 (S126)]

`primitives/IO` is an opaque built-in type, available by qualified reference without an import; bare `IO` requires an import under §8.9.1. The language has `(IO a)` and no constructors for it. User code MUST NOT construct an IO value through a constructor or pattern-match on an IO value. Values are made through `pure`, `bind`, `select`, `sleep` and platform operations, and consumed only by the runtime. The constructor is conceptually module-private; `pure` is the public interface.

The general constructor-arm requirement for `match` (§6.1) also refuses
wildcard-only and variable-only matches on IO. IO exposes no constructors
with which to satisfy that requirement; no IO-specific matching rule is
needed.

`IO a` represents a deferred computation that will produce a value of type `a` when forced. For example:

- `IO Int` -- a deferred computation that produces an integer
- `IO String` -- a deferred computation that produces a string
- `IO (Option Int)` -- a deferred computation that produces an optional integer

### 10.1.1 Type System Integration [S124 — partial / fixture migration; was Tested tests/spec_10_io::io_propagates_into_inferred_return_type (evidence delta §14.14, row 38)]

`IO` participates in the type system through standard Hindley-Milner inference. There are no special type-checking rules for `IO` -- its effect-tracking properties emerge from standard Hindley-Milner inference:

- A function that calls a platform operation (e.g., `print`) returns `IO` because the platform operation returns `IO`, and the function's return type unifies with the call result.
- A function that does not call any IO operation has no `IO` in its return type.
- A function that calls an IO-returning function inherits `IO` in its own return type.

This means that **IO propagates upward through the call graph automatically** via type inference, without any special rules or annotations.

### 10.1.2 Purity Guarantee [Tested+Neg tests/spec_10_io::io_value_in_pure_position_is_type_error_neg]

A function whose result type contains no `IO` has this guarantee: executing its result cannot cause an effect. Calling any Cranelisp function performs no effect (§3.2.3), including a function returning `IO`. The type system distinguishes the results: an `IO` value cannot be used where a non-`IO` value is expected.

```clojure
(defn add [x y] (+ x y))         ; add :: (Fn [Int Int] Int) -- non-IO result
(defn greet [name]                ; greet :: (Fn [String] (IO Int)) -- IO result
  (print (str-concat "hello " name)))
```

## 10.2 `pure` [Tested tests/spec_10_io::s124_io_opaque_pure_info, tests/opaque_io::s125_io2_applied_scalar_run, tests/opaque_io::s125_io2_passed_heap_link, tests/opaque_io::s125_io2_twice_forced_heap_balances — applied, passed, bound, captured and stored, scalar and heap, in every mode (30 IO-2 cells); one identity under the standard prelude is a stdlib conformance check (T-PURE-ID)]

```
primitives/pure :: (Fn [a] (IO a))
```

`primitives/pure` is a public built-in function that lifts a value into IO without performing a side effect. It exposes no IO constructor.

The name `pure` denotes the conventional lift of a value into `IO`, not a statement about the function's own purity.

### 10.2.2 Purpose [S10]

`pure` lifts a value into `IO a` whose execution yields that value without performing an effect. A common use case is an `if` expression with an IO branch and a non-IO branch, where both branches MUST have the same type:

```clojure
;; ERROR: branch types differ -- IO Int vs Int
(if (> x 0)
  (print (show x))    ; IO Int
  0)                   ; Int

;; OK: both branches return IO Int
(if (> x 0)
  (print (show x))    ; IO Int
  (pure 0))           ; IO Int
```

### 10.2.3 Examples [Tested tests/opaque_io::s125_io2_applied_scalar_run, tests/opaque_io::s125_io5_double_display, tests/opaque_io::s125_io5_vector_display; the zero-argument partial application `(primitives/pure)` has no cell]

```clojure
(pure 42)              ; :: (IO Int)
(pure "hello")         ; :: (IO String)
(pure true)            ; :: (IO Bool)
(pure None)            ; :: (IO (Option a))
```

`pure` is NOT a special form -- it is an ordinary function. It can be passed as a value, partially applied, or used anywhere a function `(Fn [a] (IO a))` is expected.

## 10.3 `bind` [S124 — partial / fixture migration; was Tested tests/spec_10_io::bind_triple_chain (evidence delta §14.14, row 40)]

```
primitives/bind :: (Fn [(IO a) (Fn [a] (IO b))] (IO b))
```

`primitives/bind` is a **built-in function** that composes an IO computation with a continuation, deferring execution until the runtime forces the resulting IO value (Section 10.8).

### 10.3.1 Semantics [S124 — partial / fixture migration; was Tested tests/spec_10_io::bind_pure_to_pure_plus_one (evidence delta §14.14, row 41)]

Calling `bind` performs no effect. When the runtime executes the resulting IO value, it first executes the inner IO computation, then passes its result to the continuation and executes the IO value the continuation returns.

### 10.3.3 Examples [Tested tests/spec_10_io::bind_nested_chain]

```clojure
;; Extract print's return value and use it
(bind (print "hello")
  (fn [result] (pure (+ result 1))))    ; result is the Int returned by print

;; Chain multiple IO actions
(bind (print "first")
  (fn [_]
    (bind (print "second")
      (fn [_] (print "third")))))
```

The nested continuation style can become deeply indented. The `bind!` macro (Section 10.5) provides syntactic sugar for flattening these chains.

## 10.4 Expression Sequencing (Example: `do` Macro) [S124 — library-only; was Tested tests/spec_11_stdlib::macro_do_returns_last (evidence delta §14.14, row 42)]

This subsection is a non-normative library illustration (§9.10). Its
sequencing behavior follows from the expanded `primitives/bind` calls, not
recognition of the macro name by the compiler.

```clojure
(do expr1 expr2 ... exprN)
```

`do` is a library macro (not a language requirement) that sequences expressions, discarding intermediate results. It returns the value of the last expression.

### 10.4.1 Expansion [S124 — partial / native witness; was Tested tests/spec_platforms::bind_chain_print_sequence_with_pure_terminator_emits_all (evidence delta §14.14, row 43)]

`do` expands to nested `bind` calls with anonymous continuation closures:

```clojure
(do e1 e2 e3)
;; expands to:
(bind e1 (fn [_] (bind e2 (fn [_] e3))))
```

The general form:

```clojure
(do e1 e2 ... en)
;; expands to:
(bind e1 (fn [_] (bind e2 (fn [_] ... (bind e(n-1) (fn [_] en)) ...))))
```

### 10.4.2 Semantics [S124 — library illustration / no direct witness; was S10 (evidence delta §14.14, row 44)]

`do` is **IO-specific** -- all expressions MUST have type `IO _`. Each intermediate expression's result is discarded (bound to `_` in the continuation). The type of the `do` block is the type of the last expression.

For expression sequencing without executing IO values, use `let [_ expr1] expr2` instead (§10.8).

```clojure
;; IO context: all expressions return IO, block type is IO Int
(defn main []
  (do
    (print "hello")          ; IO Int, result discarded
    (print "world")          ; IO Int, result discarded
    (print "done")))         ; IO Int, returned
```

### 10.4.3 Examples [S124 — library illustration / no direct witness; was S10 (evidence delta §14.14, row 45)]

```clojure
(defn greet-twice [name]
  (do
    (print (str-concat "hello " name))
    (print (str-concat "goodbye " name))))

(defn main []
  (do
    (print (show 42))
    (print (show 100))))
```

## 10.5 Monadic Bind Sugar (Example: `bind!` Macro) [S124 — library-only; was Tested tests/spec_11_stdlib::macro_bind_bang_single_binding (evidence delta §14.14, row 46)]

This subsection is a non-normative library illustration (§9.10). Its
sequencing behavior follows from the expanded `primitives/bind` calls, not
recognition of the macro name by the compiler.

```clojure
(bind! [name1 io-expr1
        name2 io-expr2
        ...]
  body)
```

`bind!` is a library macro (not a language requirement) that provides syntactic sugar for monadic bind chains. It desugars to nested `bind`/`fn` calls, making sequential IO operations with named intermediate results readable.

### 10.5.1 Expansion [S124 — library illustration / no direct witness; was S10 (evidence delta §14.14, row 47)]

Single binding:

```clojure
(bind! [x (read-line)]
  (print x))
;; expands to:
(bind (read-line) (fn [x] (print x)))
```

Multiple bindings:

```clojure
(bind! [line (read-line)
        result (pure (parse-int line))]
  (match result
    [(Some n) (pure n)
     None (pure 0)]))
;; expands to:
(bind (read-line) (fn [line]
  (bind (pure (parse-int line)) (fn [result]
    (match result
      [(Some n) (pure n)
       None (pure 0)])))))
```

### 10.5.2 Semantics [S124 — library-only / partial; was Tested tests/spec_11_stdlib::macro_bind_bang_sequential_reference (evidence delta §14.14, row 48)]

Each binding pair `name io-expr` evaluates `io-expr` (which MUST produce an `IO a`), extracts the inner value via `bind`, and makes it available as `name` in subsequent bindings and the body.

The bindings are evaluated left-to-right. Each binding can reference names introduced by earlier bindings. The body expression is evaluated in the scope of all bindings and MUST produce an `IO b` value.

### 10.5.3 Comparison with `do` [S124 — library illustration / no direct witness; was S10 (evidence delta §14.14, row 49)]

`do` discards intermediate values -- use it when you only care about sequencing effects. `bind!` names intermediate values -- use it when you need the results of earlier IO operations:

```clojure
;; do: sequence effects, discard results
(do
  (print "enter name:")
  (print "enter age:"))

;; bind!: sequence effects, use results
(bind! [name (read-line)
        age (read-line)]
  (print (str-concat "hello " (str-concat name (str-concat " age " age)))))
```

## 10.6 Entry Point [Tested+Neg tests/spec_10_io.rs::batch_main_pure_int_return_is_rejected, tests/spec_10_io.rs::s124_main_location_arity_run, tests/spec_10_io.rs::s124_main_location_arity_link, tests/spec_10_io.rs::s124_main_missing_definitions_run, tests/spec_10_io.rs::s124_main_missing_definitions_link — a non-`IO` return, a `main` with a parameter and an entry with no `main` are refused under `--run` and `--link`; the controls are `s124_main_control_5_run` and `s124_main_control_7_run`]

Batch programs MUST define an ordinary function named `main` with no parameters. The return type of `main` MUST be `IO _` (IO of any type):

```
main :: (Fn [] (IO _))
```

A trait method named `main` does not define the program's `main`; a batch program whose only `main` is a trait method MUST be refused as having no `main`. [Tested+Neg tests/spec_10_io.rs::s124_main_missing_trait_method_run, tests/spec_10_io.rs::s124_main_missing_trait_method_link — refused as an entry with no `main`, with no position; the control `s124_main_control_5_run` exits 5]

A multi-arity definition `(defn main ([] …) ([x] …))` does not satisfy the entry-point requirement and MUST be refused even though it has a zero-argument variant. [Tested+Neg tests/spec_10_io.rs::s124_main_location_overload_run, tests/spec_10_io.rs::s124_main_location_overload_link — refused, not run as its zero-argument clause, and located at the definition; the control `s124_main_control_7_run` exits 7]

The `main` function is the entry point for batch-mode execution. When a program is run with `cranelisp --run file.cl`, the compiler locates and invokes `main` after compilation.

### 10.6.1 Exit Code [Tested+Neg tests/spec_10_io.rs::main_returning_io_string_exits_zero_run_and_linked, tests/spec_10_io.rs::main_returning_io_bool_exits_zero_run_and_linked, tests/spec_10_io.rs::run_mode_main_returns_pure_exit_code, tests/spec_10_io.rs::run_mode_main_returns_pure_nonzero, tests/link.rs::link_hello_produces_executable_with_main_exit_code, tests/spec_10_io.rs::batch_main_pure_int_return_is_rejected — an `Int` inner value is the exit code under `--run` and in the linked executable; `String` and `Bool` inner values exit 0 with empty stdout under both; a non-`IO` `main` is rejected]

The inner value of `main`'s return determines the program's exit code. When `main` returns `IO Int`, the integer value is used as the process exit code. For any other inner type, the exit code MUST be 0.

```clojure
(defn main []
  (do
    (print "hello")
    (pure 0)))          ; exit code 0

(defn main []
  (print "hello"))      ; print returns IO Int (0), so exit code is 0
```

### 10.6.2 REPL Mode [Tested tests/spec_10_io.rs::repl_io_notice_precedes_effect_output_neg_not_on_pure_defn_or_lookup_turns]

In REPL mode, there is no `main` function requirement. Expressions are evaluated interactively. The language defines which expressions are IO actions — those of type `IO a` (§10.1). The REPL executes such an expression through the trampoline (§10.8), so its effects occur; that execution and its presentation are specified by [`repl/spec/01-display-format.md` §1.2.1](../repl/spec/01-display-format.md#121-io-expression-results).

### 10.6.3 Mode-Output Equivalence [Tested tests/output_equivalence::output_equiv_single_print]

A program's **observable output is identical across all run modes**. The same program, executed under `--run` (JIT), under a `--link`-produced standalone binary, or by entering its forms at the REPL, MUST produce byte-for-byte identical observable effects (the stream of `print` / `read-line` and other platform-effect interactions, in the same order). The run mode determines only *how* the program is built and invoked — not *what* it observably does. The IO task tree and its trampoline interpretation (§10.8) are mode-independent, so the effects forced are the same in every mode. (This is the IO-specific instance of the general cross-mode equivalence guarantee; cf. the `(trace ...)` "behaves identically across modes" guarantee at §[4.12.9](04-expressions.md#4129-build-mode-availability).)

## 10.7 Effect Tracking [Tested tests/spec_10_io::defn_returning_pure_displays_fn_type]

IO effects are tracked entirely through the type system, using standard type inference. There are no special annotations, keywords, or compiler flags for effect tracking.

### 10.7.1 Propagation [Tested tests/spec_10_io::defn_returning_pure_displays_fn_type]

When a function calls an IO-returning operation, the IO type propagates to the function's own return type:

```clojure
(defn greet [x]          ; inferred: (Fn [String] (IO Int))
  (print x))

(defn greet-num [x]      ; inferred: (Fn [Int] (IO Int))
  (print (show x)))

(defn double-greet [x]   ; inferred: (Fn [Int] (IO Int))
  (do
    (print (show x))
    (print (show (+ x 1)))))
```

Functions whose result types contain no `IO` include:

```clojure
(defn add [x y]          ; inferred: (Fn [Int Int] Int)
  (+ x y))

(defn double [x]         ; inferred: (Fn [Int] Int)
  (* x 2))
```

### 10.7.2 Branch Consistency [Tested tests/spec_10_io::if_both_branches_io]

Both branches of an `if` expression MUST have the same type. When one branch returns IO and the other has a non-IO result, the non-IO branch MUST be wrapped with `pure` to produce a matching `IO` type:

```clojure
;; ERROR: (IO Int) vs Int
(if condition
  (print "yes")
  42)

;; OK: both branches are (IO Int)
(if condition
  (print "yes")
  (pure 42))
```

The same applies to `match` arms -- all arms MUST have the same type, so if any arm returns IO, all arms MUST return IO.

## 10.8 Deferred Execution (Task + Trampoline) [S124 — insufficient former witness; was S122 — rollup of children: §10.8.3 and §10.8.4 are pending; this heading's own deferral prose is covered by tests/spec_10_io::io_values_deferred (evidence delta §14.14, row 50)]

Cranelisp uses **deferred evaluation** for IO operations. When the program reaches a call to a platform operation, an IO value describes the effect but does NOT execute it. The effect executes only when the runtime's trampoline loop forces the IO task tree.

```clojure
(some-platform-op "hello")  ; returns an IO value -- effect not yet performed
```

### 10.8.1 Task Tree Construction [S124 — partial / module seam and migration; was Tested crates/cranelisp-intrinsics/src/io/tests.rs::test_run_io_pure — the reuse sentence below is banded at the sentence; a reused poll-shape leaf is nonconforming (evidence delta §14.14, row 51; S125 evidence delta §28.2)]

IO values are **descriptions of deferred work**, not results:

- A platform operation call returns an IO value describing the effect to execute when forced.
- `(bind io cont)` returns an IO value composing the computation with the continuation.
- `(pure 42)` returns an IO value that yields `42` without performing an effect.
- Effects only execute when the runtime forces the IO value.

A description is **reusable**: forcing an IO value does not consume it, so the same IO value MAY be forced more than once, and a conforming implementation MUST interpret each forcing under §10.8.2 exactly as it interprets the first rather than refusing it.
```clojure
(let [io (print "hello")]   ; io is an IO value — nothing printed
  io)                        ; returns the IO value

```

### 10.8.2 Trampoline Interpretation [S124 — partial / weak depth; was Tested tests/spec_10_io::run_mode_deep_bind_chain_named_continuation (evidence delta §14.14, row 52)]

The runtime executes an IO value according to its composition: `pure` yields its value, platform operations perform their effects, and `bind` sequences its inner computation before its continuation (§10.3.1).

IO execution is iterative — no recursion, O(1) call stack depth regardless of chain length. IO loops run indefinitely without stack growth.

### 10.8.3 Effect Isolation [S124 — no direct witness; was S10 (evidence delta §14.14, row 53)]

Because effects are deferred, they no longer escape through argument evaluation:

```clojure
(defn choose [p a b] (if p a b))
(defn main [] (choose true (print "a") (print "b")))
```

Both `(print "a")` and `(print "b")` construct IO values but do NOT execute. Since `choose` returns only one of them, only that branch's effect is present in the returned IO tree. The trampoline forces only "a" to print.

### 10.8.4 Comparison [S124 — mixed summary; was S10 (evidence delta §14.14, row 54)]

| Property | Cranelisp (Deferred) | Haskell (Lazy) |
|---|---|---|
| When effects execute | When trampoline forces the IO tree | When the runtime interprets the IO action |
| What IO values contain | Descriptions of pending effects | Descriptions of pending effects |
| Effect ordering | Determined by `primitives/bind` composition | Determined by data dependencies and `>>=` chains |
| Stack depth | O(1) — trampoline with explicit continuation stack | Implementation-dependent |
| User inspection | IO is opaque; no constructor matching (§10.1) | Possible — similar model |

## 10.9 Platform Declarations [Tested crates/cranelisp-frontend/src/module_extract/tests.rs::test_platform_extracted — the `(platform name)` form and its bare-symbol name only]

```clojure
(platform name)
```

A `(platform name)` form declares which platform DLL provides IO operations for the program. It is **only valid in the entry module**. The `name` is a bare symbol identifying the platform (e.g., `stdio`, `test-capture`).

### 10.9.1 Scope [S122 — no discriminating evidence traced here: crates/cranelisp-frontend/src/module_extract/tests.rs::test_platform_extracted only shows a top-level platform form is extracted; rejection of a platform form in a non-entry module and import of the declared platform from a non-entry module are untraced]

Platform declarations are entry-module-only:

- A `platform` form in any non-entry module is a compile-time error.
- Library and non-entry modules that need platform functions use `(import [platform.name [*]])` where `name` is the declared platform. The platform module is available once the entry module has declared it.
- Platform names are resolved via the platform DLL search order (§8.11.3).

### 10.9.2 Purpose [S10]

Platform declarations control which concrete implementations of IO operations are loaded. Each platform provides a set of functions with IO-returning types. Alternative platforms can substitute different implementations while preserving the same type signatures. User code that depends only on the type-level contract works with any conforming platform.

### 10.9.3 Syntax [S10]

The platform name is a bare symbol, not a string literal:

```clojure
(platform stdio)          ; correct — bare symbol
(platform "stdio")        ; ERROR — string literal not allowed
```

## 10.10 Platform ABI Contract [Tested tests/link::link_repeated_platform_adt_marshal_does_not_corrupt_heap — S124 re-judgment: retains narrow ABI witness (evidence delta §14.14, row 55)]

Platform libraries provide IO operations via dynamically loaded shared libraries. The contract between platform libraries and the Cranelisp runtime is defined at the C ABI level.

### 10.10.1 Calling Convention [Uncovered S122]

Platform functions use the C calling convention (`extern "C"`). All parameters and return values are `i64` at the ABI level. The interpretation of each `i64` depends on the Cranelisp type:

- `Int` -- the integer value directly
- `Bool` -- 0 for false, 1 for true
- `String` -- pointer to heap-allocated string (see [Section 12](12-runtime.md))
- `IO a` -- an opaque IO value; its representation is implementation-defined
- `Fn a b` -- not a platform ABI type. No function value crosses the platform boundary: a platform function's parameter and result types MUST NOT contain a function type, and an implementation MUST reject a platform declaration whose signature does. Containment includes type arguments and the fields of named ADTs, followed transitively (user ruling, 2026-11-15). The host callback interface (§10.10.3) provides no closure-invocation or reference-count entry. [Uncovered S122 — replaces the S-future closure-callback commitment]

### 10.10.2 IO Return Requirement [S10]

Every platform function MUST return an `IO` type — unconditionally, not only those that "appear to" perform side effects. The compiler cannot inspect foreign native code, so it cannot verify purity and MUST trust the declared signature; a platform function declared with a non-IO return type would be treated as an ordinary computation — eligible for memoization, reordering, elision, and lenient/parallel sparking — while the foreign host performs arbitrary effects, which is unsound. Requiring `IO` ensures every foreign effect is tracked and sequenced in the type system. See §[8.9.3](08-modules.md#893-platform-modules) for the full rationale; the implementation rejects any platform function whose declared return type is not `IO _`.

### 10.10.3 Allocation Callback [S124 — no direct witness / module allocation; was S10 (evidence delta §14.14, row 56)]

Platform libraries receive an allocation callback from the host runtime. This callback is used to allocate Cranelisp heap values (such as IO values and strings) using the runtime's allocator, ensuring proper memory management integration (reference counting).

### 10.10.4 Implementation-Defined Details [S10]

The specific mechanism for registering platform functions, the allocation callback interface, and the shared library discovery path are implementation-defined.

## 10.12 Automatic IO Scheduling [S124 — partial / wrong former summary witness; was Tested tests/spec_10_io::resource_serial_same_token_serializes (evidence delta §14.14, row 57)]

There is no `par-bind!` form in the language. Concurrent IO is automatic: the
compiler MUST perform independence analysis on core `primitives/bind` chains
and MUST compose commutative, data-independent effect pairs for parallel
execution. A chain is nested application of `primitives/bind` with one-parameter
`fn` continuations, after macro expansion. Bindings below name those continuation
parameters and their associated IO operands. Source order is the sequential
order of that composition. No `do` or `bind!` spelling is required or recognised
for this obligation; the examples use their non-normative sugar (§10.4–§10.5).

### 10.12.1 Semantics [S124 — partial / over-strong timing; was Tested tests/spec_10_io::auto_io_independent_diff_token_parallelizes_e2e (evidence delta §14.14, row 58)]

The compiler performs an independence analysis on each core `primitives/bind` chain. For a pair of bindings `(xi, ei)` and `(xj, ej)`:

- **Data independence**: `xi` is not free in `ej`, and `xj` is not free in `ei`.
- **Commutativity**: both `ei` and `ej` call a platform function whose manifest declares `SchedulingClass::Commutative`.

When both conditions hold, the compiler composes the effects for parallel execution. The runtime MAY then execute the branches concurrently; the execution mechanism is implementation-internal and not prescribed (see §10.12.5 and §10.12.6). [S124 — partial / same issue; was S94 (evidence delta §14.14, row 59)]

Effects between Sequential bindings are always executed in source order. Effects between Commutative bindings MAY execute in any order. Correct programs MUST NOT depend on the relative ordering of effects within a set of Commutative bindings.

### 10.12.2 Platform Scheduling Classes [Tested tests/spec_10_io::auto_io_sequential_class_stays_serial_e2e, crates/cranelisp-backend/src/compiler/control_flow/par_codegen_tests.rs::sequential_let_emits_no_par_node — Sequential class only; Commutative and ResourceSerial are evidenced under §10.12.1 and §10.12.4]

Platform functions declare their scheduling class in the manifest. Users do not annotate effects directly.

| Class | Meaning | Examples |
|---|---|---|
| `Sequential` | Ordered relative to other calls to this function | `read-line`, `print` |
| `Commutative` | Freely reorderable; no shared state between calls | `http-get`, `time-now` |
| `ResourceSerial` | Parallel unless runtime resource tokens conflict | `file-read(fd)`, `log(handle, msg)` |

### 10.12.3 Examples [S11]

```clojure
;; Compiler parallelises: both http-get calls are Commutative + data-independent
(bind! [response1 (http-get "url1")
        response2 (http-get "url2")]
  (pure (process response1 response2)))

;; Compiler preserves order: read-line is Sequential
(bind! [line1 (read-line)
        line2 (read-line)]
  (pure (str-concat line1 line2)))
;; line1 is always the first line read, line2 the second
```

### 10.12.4 Runtime Resource Tokens [S124 — partial; was Tested tests/spec_10_io::resource_serial_same_token_serializes (evidence delta §14.14, row 60)]

`ResourceSerial` platform functions associate a runtime resource token with their effect (a non-zero i64 that uniquely identifies the resource they access). Within a parallel group, the trampoline:

1. Groups effects by resource token.
2. Runs branches with `token=0` (unrestricted) each independently and concurrently (via whatever execution mechanism the implementation provides — see §10.12.5).
3. For each non-zero token group, runs all branches in that group sequentially as a single work item.

Branches in different token groups run concurrently; branches with the same non-zero token are serialised regardless of data independence, **and execute in source order** — the sequential order of their core `primitives/bind` composition. Mutual exclusion alone is insufficient: same-resource effects are observable in their relative order (e.g. successive appends to one log file, or ordered writes to one file descriptor), so a same-token group preserves source order, not merely the property that its branches do not overlap. A conforming implementation MUST NOT reorder the effects within a single non-zero token group.

The serialisation in this subsection is the limiting case (one effect at a time) of the more general **resource capacity** of §10.12.4.1.

### 10.12.4.1 Resource Capacity — Token Pools [S124 — partial / timing classification; was S95 (evidence delta §14.14, row 61)]

§10.12.4 describes the case in which a resource admits **one** effect at a time. A resource may instead admit several concurrently. The platform characterises each resource by a **capacity** *N* — the number of effects on that resource that may safely be in flight at once (the size of the resource's *token pool*). Capacity generalises the scheduling classes of §10.12.2: capacity 1 is `ResourceSerial`; an unrestricted (`token = 0`) effect has effectively unbounded capacity.

**Capacity attaches to the resource (the token), NOT to the effect.** A resource is identified by its non-zero token; its capacity is a property of that token, not of any single effect that uses it. This is load-bearing:

| # | Requirement | Status |
|---|---|---|
| 1 | Effects on **distinct** tokens have **independent** capacities — each token's pool is bounded only by its own capacity. | [S95] |
| 2 | Effects sharing **one** token share that resource's single pool — the total number in flight across **all** effects on the token MUST NOT exceed the token's capacity *N*, regardless of which distinct effects they are. (Canonical case: distinct effects — e.g. `query`, `execute`, `begin` — drawing from one connection pool of *N* connections; the sum in flight ≤ *N*.) | [S95] |
| 3 | Within a parallel group, for a non-zero token of capacity *N*: up to *N* effects on that token MAY run concurrently; while *N* are in flight, any further effect on the token **parks** — it MUST NOT begin until one of the in-flight effects completes and frees a permit. The (N+1)th effect's deferral is observable as wall-clock latency (and, informatively, as a park/resume in the dev-facing strand stream of §10.12.6). | [S124 — retains ceiling; partial whole row; was S95 (evidence delta §14.14, row 62)] |
| 4 | Capacity 1 is exactly the `ResourceSerial` behaviour of §10.12.4: at most one effect on the token runs at a time, the rest serialise, **and they execute in source order** (exclusion *and* order). | [S95] [S125 — Tested tests/spec_10_io::run_mode_fresh_poll_leaf_per_in_flight_force_control for two fresh poll leaves on `select` branches; nonconforming for one reused leaf forced on both branches, RED tests/spec_10_io::run_mode_reused_poll_leaf_in_flight_capacity_one_serialises] |
| 5 | For capacity *N* ≥ 2 the up-to-*N* concurrently-admitted effects MAY overlap and MAY complete in any order; a correct program MUST NOT depend on their relative ordering. Source ordering is guaranteed only within a capacity-1 token (item 4). | [S95] |
| 6 | A `token = 0` (unrestricted) effect acquires no permit and is bounded by no pool (§10.12.4 step 2); this is unchanged. | [S95] |

Capacity is part of the platform's concurrency contract and is a **trust boundary**, continuous with the rest of §10.12: the compiler does not verify a declared capacity, exactly as it does not verify a `Commutative` claim or a `ResourceSerial` token. By declaring a resource's capacity *N*, the platform author asserts that up to *N* effects on that resource may run concurrently; the language takes this assertion on faith and does not check it. Exceeding *N* would be a correctness violation, which the capacity ceiling exists to prevent.

This description is **observational and mechanism-neutral** (consistent with §10.12.5): it constrains *what a program observes* — how many effects on a given token overlap, and that an effect beyond the token's capacity does not begin until a permit frees — not *how* the trampoline realises the pool. A conforming implementation MAY realise a capacity-*N* token with a counting semaphore of *N* permits keyed by the token, a bounded work queue, or purely sequential execution (which also conforms, admitting one effect at a time), provided the observable behaviour above holds. The strict within-token source ordering of §10.12.4 is a property of the capacity-1 case and, like that case, MUST be carried deliberately: a bounded pool of permits gives *exclusion* (an *N*-bound on concurrency) but not *order*, so a capacity-1 token preserves source order while a capacity-*N* token (item 5) imposes none.

Capacity is the platform-asserted *ceiling*. A separate, program-chosen in-flight throttle — the **degree** — composes with it; see §10.12.4.2.

### 10.12.4.2 Admission Degree — Program-Chosen Throttle [S96]

§10.12.4.1 specifies **capacity**: the platform-asserted ceiling on how many effects a resource may *safely* sustain. A program may additionally impose its own, stricter, in-flight limit — the **degree** — for reasons of its own: bounding memory, ensuring fairness across requests, or being polite to a remote service. Capacity and degree are different concepts owned by different parties:

| Aspect | capacity (§10.12.4.1) | degree |
|---|---|---|
| Asserted by | the **platform** | the **program** |
| Attaches to | the **resource** (the token) | the program's policy (a token, or globally) |
| Concern | **correctness** — exceeding it is unsafe (a trust boundary) | **policy** — memory / fairness / politeness; never a safety claim |
| Effect of violating | undefined / unsafe behaviour (the ceiling exists to prevent it) | none possible — over-degree work simply parks |

Requirements:

| # | Requirement | Status |
|---|---|---|
| 1 | When a program sets a degree *D* on a resource of capacity *N*, the effective in-flight limit on that token is `min(N, D)`. At most `min(N, D)` effects on the token MAY be in flight; a further effect **parks** until one frees — the same observable park as the (N+1)th-parks of §10.12.4.1 (wall-clock latency / backpressure), not an error. | [S96] |
| 2 | A degree set above the resource's capacity has no additional effect: capacity still bounds (`min(N, D) = N`). Degree can only *tighten* the limit, never loosen it past the platform-asserted ceiling. | [S96] |
| 3 | A program MAY also set a **global** degree bounding the total number of in-flight **detached strands** (§10.12.7) across all tokens. The accept loop of a server emits launched effects unboundedly (§4 of the model); this global bound is what keeps the fan-out's memory bounded — the over-bound launch parks until an in-flight detached strand completes. | [S96] |
| 4 | Over-degree parking NEVER drops or fails work; it only **defers** it. Backpressure is observable as latency, not as a lost effect or an error result. | [S96] |

Degree is **policy, not a trust boundary**: unlike a capacity claim (which the language takes on faith and whose violation is unsafe), a degree is merely a self-imposed throttle and can never be unsound — at worst it slows the program down. The means by which a program selects a degree (a deployment- or runtime-configuration value) is **implementation-defined**; degree is **not** a language form. This subsection constrains only what a program observes when a degree is in force — that at most `min(capacity, degree)` effects of a kind are in flight and the rest park — not how the runtime realises the throttle.

### 10.12.5 Runtime Mechanism [S124 — partial / mechanism-neutrality; was S11 (evidence delta §14.14, row 63)]

> **Superseded failure policy (2026-11-28):** the panic/runtime-error or
> platform-failure policy below is subject to [S125-Q12](appendix-d-open-questions.md#s125-q12-what-happens-when-a-macro-clause-raises-an-otherwise-unspecified-hardware-trap).
> The older wording is retained pending the next-sprint rewrite.

The compiler composes parallelisable effect pairs. The runtime MAY execute their branches concurrently, subject to resource token serialisation; results are collected and passed to the continuation. **The concurrency mechanism is implementation-internal and not prescribed** — consistent with the non-prescriptive runtime stance of [§12.1](12-runtime.md#121-value-representation). A conforming implementation MAY use a worker thread pool, a single-threaded reactor on which effects that wait (for example on I/O readiness) suspend and resume so that independent waits overlap, any combination of the two, or purely sequential execution (which also conforms — see [§12.4.3](12-runtime.md#1243-lenient-evaluation)). Whatever the mechanism, observable behaviour MUST satisfy §10.12.1–§10.12.4 and remain observationally identical to sequential left-to-right execution (§10.12.6, [§12.4.3](12-runtime.md#1243-lenient-evaluation)). The current implementation uses two mechanisms — a rayon worker pool for CPU/blocking work and a host-owned reactor on which poll-shape effects suspend and resume — described in `design/arch/effect-concurrency.md`. [S94]

### 10.12.6 Execution Substrate and Slice Delivery (informative) [S93]

> This subsection is **informative**: it records the disposition of the
> concurrency model's execution substrate. It introduces **no new user-visible
> language surface** and imposes no requirement beyond those already stated in
> §10.12.1–§10.12.5 and [§12.4.3](12-runtime.md#1243-lenient-evaluation).

The automatic scheduling of §10.12 is realised by an **execution substrate** — a
host-owned reactor that may overlap independent effects, and that may run
same-token effects under bounded resource pools — being delivered incrementally
("in slices"). Three facts fix what this means for the language:

1. **The substrate changes execution, not extraction.** The independence and
   token analysis of §10.12.1 and §10.12.4 stand verbatim. The substrate only
   changes *how* the extracted-concurrent work is run, never *which* work is
   eligible. Its results are **observationally identical to sequential
   left-to-right execution** under the equivalence already guaranteed by
   §12.4.3 (and the within-token source ordering pinned in §10.12.4). A program
   cannot distinguish the substrate from a conforming sequential implementation.

2. **The substrate, the per-effect concurrency descriptor (a generalisation of
   the §10.12.2 scheduling classes), and the strand-correlated observability
   event stream are implementation- and tooling-facing — not language features.**
   They are not invokable from cranelisp source, carry no in-language type, and
   produce no value a program can observe. In particular the **strand identity**
   (the correlation id threaded through the substrate for debugging and tracing)
   is a **dev/observability concern only**; it is not a queryable language value
   at this stage. It surfaces, if at all, through REPL/dev-facing diagnostic
   sinks (a sibling of [`trace`](04-expressions.md#412-trace-expression) and
   `io_trace`), which are outside the normative language surface.

3. **The explicit control surface is now fully specified.** **Launch-and-continue
   (un-joined) effects and process termination on panic** are specified
   in §10.12.7 (launch-and-continue) and
   [§12.7.9](12-runtime.md#1279-supervised-detached-strands) (panic termination),
   together with the program-chosen admission **degree** of §10.12.4.2. The
   typed control-combinator layer — `race` / `select`, a derived `timeout`, and
   the structured cancellation underneath them — is specified in §10.12.8
   (combinators), §10.12.9 (cancellation), and §10.12.10 (the reference control
   patterns: graceful shutdown, cancel-on-disconnect, per-request timeout), with
   its typing and runtime semantics in
   [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation).
   The control surface — like a detached strand — is the **explicit-control**
   half of the model and is deliberately outside the §10.12.1–§10.12.5
   sequential-equivalence guarantee (it abandons effects by design); the inferred
   half remains observationally identical to sequential execution.

### 10.12.7 Launch-and-Continue (Detached Effects) [S124 — partial rollup; was S96 (evidence delta §14.14, row 64)]

> **Superseded failure policy (2026-11-28):** the panic/runtime-error or
> platform-failure policy below is subject to [S125-Q12](appendix-d-open-questions.md#s125-q12-what-happens-when-a-macro-clause-raises-an-otherwise-unspecified-hardware-trap).
> The older wording is retained pending the next-sprint rewrite.

The automatic scheduling described so far concerns effects whose completion the continuation **awaits** — the structured fork-join of [§12.4.3](12-runtime.md#1243-lenient-evaluation), in which every branch joins before the enclosing expression returns. An effect may instead be **launched and not joined**: run concurrently with the continuation, which proceeds **without awaiting it**. This is **launch-and-continue** — the mechanism by which a server fans out request handlers with **no `spawn`** in the source.

**Eligibility.** An effect is eligible to be launched-and-continued when **both**:

1. its **result is discarded** — it occupies a non-final statement position whose bound value is unused (for example, an effect ahead of the continuation in a core `primitives/bind` chain whose continuation parameter is unused), so no later computation can observe its result; and
2. its **resource tokens are disjoint** from the continuation's effects (§10.12.4), so it cannot conflict with any subsequent effect.

In `(primitives/bind (handle-conn conn) (fn [_] (serve listener)))`, the result of `handle-conn` is unused over a per-connection token disjoint from `serve` — it is eligible. `serve` recurses to accept the next connection **without waiting** for `handle-conn` to complete, and the accept loop fans out automatically. No annotation appears in the handler.

**Observable contract.** When an eligible effect is launched as a **detached strand**:

| # | Requirement | Status |
|---|---|---|
| 1 | The detached strand runs **concurrently** with the continuation; the continuation MUST NOT block on its completion. | [S124 — retains current detached witness; was S96 (evidence delta §14.14, row 65)] |
| 2 | The launching strand **never observes** the detached effect's **result** — guaranteed trivially by eligibility (the result is discarded). | [S124 — partial / constructive eligibility; was S96 (evidence delta §14.14, row 66)] |
| 3 | **User ruling, 2026-11-15:** a runtime panic in a detached strand ends the whole process ([§12.7.9](12-runtime.md#1279-supervised-detached-strands)); it is not recovered by a supervisor. | [Tested+Neg tests/concurrency_fanout::detached_faulting_effect_exits_the_process, tests/concurrency_fanout::launch_and_continue_runs_concurrently_launcher_does_not_await — S124 re-judgment: retains panic clause (evidence delta §14.14, row 67)] |
| 4 | The in-flight count of detached strands is bounded by the admission **degree** (§10.12.4.2 item 3), not by source structure: the accept loop emits launches unboundedly and the global degree throttles execution (over-bound launches park). | [S124 — retains with fixture limit; was S96 (evidence delta §14.14, row 68)] |
| 5 | **Cancellation ownership.** A detached strand executes in the **cancellation context** in which its launch is executed ([§10.12.9](#10129-structured-cancellation)) and is cancelled when that context is cancelled. Leaving the launching function, or completion of the effect that launched it, does not cancel it. Otherwise it runs to completion. | [Uncovered S122 — new obligation] |
| 6 | **Drain on normal completion (user ruling, 2026-11-15: a panic instead ends the process).** When the program's top-level effect (`main`, §10.6) completes normally, the program terminates only after every outstanding detached strand has finished: completed or been cancelled (§10.12.9). | [Uncovered S122 — new obligation] |

**Relationship to the observational-equivalence guarantee.** A detached strand changes timing: it overlaps the continuation rather than completing before it. Its discarded result does not change the program's value. Whether an eligible effect runs detached, inline or on a worker remains implementation-determined. Its cancellation context follows the program's effect structure (item 5), independently of that scheduling choice. A panic ends the process in every case (§12.7; user ruling, 2026-11-15). The TCO interaction is pinned in [§12.5](12-runtime.md#125-tail-call-optimization).

### 10.12.8 Structured Control Combinators — `race` / `select` / `timeout` [S124 — partial / surface split; was S96 (evidence delta §14.14, row 69)]

> **Superseded failure policy (2026-11-28):** the panic/runtime-error or
> platform-failure policy below is subject to [S125-Q12](appendix-d-open-questions.md#s125-q12-what-happens-when-a-macro-clause-raises-an-otherwise-unspecified-hardware-trap).
> The older wording is retained pending the next-sprint rewrite.

The scheduling of §10.12.1–§10.12.7 is **inferred**: the compiler extracts concurrency from dataflow independence, and a program neither requests nor observes it beyond its timing. This subsection specifies the **explicit-control** half — a small set of in-language combinators by which a program **explicitly** runs effects against one another and bounds them in time. They are the irreducible vocabulary for an uncooperative I/O boundary (a slow peer, a client that disconnects, a request that must not outlive its deadline) — the cases the inferred half cannot reach because they require the program to choose what to *abandon*.

The combinators are **ordinary typed functions**, not special forms and not platform effects: each takes `IO` value(s) and **constructs a new `IO` value** describing the concurrent composition (with automatic parallel composition governed by §10.12.5). They are pure with respect to construction — building the `IO` runs nothing — and the composed effect runs only when the resulting `IO` is itself sequenced into the program's effect (via `primitives/bind` composition) and reaches the trampoline. Their typing and runtime semantics are pinned in [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation); this subsection states the **observable contract**.

`primitives/select` and `primitives/sleep` are language-provided operations.
`race` and `timeout` below are non-normative library derivations; their
observable descriptions explain the core operations they compose, and do not
require those library names. `race a b` is `(primitives/select [a b])`.
A `timeout` maps the effect's value to `primitives/Some`, maps the timer's value
to `primitives/None`, and selects between them. These mappings use
`primitives/bind` and `primitives/pure`; no library `map` or `Functor` is needed.
The cancellation rules apply to the underlying `select` branches.

| Combinator | Indicative type | Observable result |
|---|---|---|
| `race` | `IO a -> IO a -> IO a` | Runs both effects concurrently; completes with the value of the **first to complete**. The other (the **loser**) is **cancelled** (§10.12.9). |
| `select` | `Vec (IO a) -> IO a` | The *n*-ary generalisation of `race` over a homogeneous **vector**: runs all effects concurrently, completes with the value of the first to complete; **all other branches are cancelled** (§10.12.9). `select [a, b]` is observationally equivalent to `race a b` (the `[..]` literal is a `Vec`, not a `List`). The empty vector `select []` has no branch that can win — it MUST raise a runtime error (see "Empty `select`" below), not return a value. |
| `timeout` | `Int -> IO a -> IO (Option a)` | Runs the effect against a timer of duration *d* **milliseconds** (see "Duration unit" below). Completes with `(Some v)` if the effect completes first (value *v*), or `None` if the timer fires first — in which case the effect is **cancelled** (§10.12.9). Derived: `timeout d io` ≡ `race` of `io` against a `(sleep d)` timer (the stdlib derivation; see [§11](11-stdlib.md)). |

**Observable contract.**

| # | Requirement | Status |
|---|---|---|
| 1 | `primitives/select` completes with the value of **exactly one** branch — the **winner**, the first branch to complete. Exactly one branch's value is returned; every other branch is cancelled and its value is **never** returned or observed. | [S124 — retains value; cancellation partial; was S96 (evidence delta §14.14, row 70)] |
| 2 | **Determinism of the winner.** The winner is the branch that **completes first** in wall-clock time. When two or more branches have completed before the runtime observes either, **which of the completed branches wins is unspecified** (it is NOT guaranteed to be the source-order-first branch). A program MUST NOT depend on which of several simultaneously-ready branches is chosen. A program that needs a deterministic tie-break MUST encode it (e.g., order-sensitive branches that cannot complete simultaneously). | [S124 — retains separated winner; was S96 (evidence delta §14.14, row 71)] |
| 3 | **`primitives/select` returns only the winner's value, not its index.** The combinators do not report *which* branch won. A program that must distinguish the winner encodes the discriminant in each branch's result type — e.g., each branch uses `primitives/bind` and `primitives/pure` to wrap its result in a user-declared tag — so the returned value itself identifies the source. (This keeps the combinator set minimal; an index-returning variant is derivable and not primitive.) | [S124 — retains value/index discriminator; example unbuilt; was S96 (evidence delta §14.14, row 72)] |
| 4 | **Losers are cancelled, not merely ignored.** A losing branch is not left running to completion with its result discarded; it is **cancelled** per §10.12.9 — its in-flight effect does not run to its completion side-effect, and its resources are released. This is the load-bearing difference from launch-and-continue (§10.12.7), where the detached effect is never awaited and runs to completion unobserved unless its cancellation context is cancelled (§10.12.7 item 5). | [S124 — partial / core versus library; was Tested+Neg tests/concurrency_cancellation::race_loser_completion_side_effect_absent_neg, tests/concurrency_cancellation::select_only_winner_value_returned_losers_side_effects_absent_neg, tests/concurrency_cancellation::race_loser_releases_resource_permit — direct combinator branches; the contrast clause's launched-work cancellation is §10.12.7 item 5's obligation (ACT-0977) (evidence delta §14.14, row 73)] |
| 5 | **Derived library illustration:** `timeout` returns `None` **only** when the timer fired before the effect completed; on `None` the wrapped effect is cancelled (§10.12.9). `timeout` returning `(Some v)` guarantees the effect completed normally and the timer was cancelled. The two outcomes are mutually exclusive. | [S124 — library illustration; was S96 (evidence delta §14.14, row 74)] |

**Duration unit.** The language has no dedicated `Duration` type; a duration is an ordinary `Int`. Both `sleep`'s argument and `timeout`'s deadline *d* are an `Int` count of **milliseconds**. `(sleep 100)` parks for ≈100 ms and resolves with `0`; `(timeout 100 io)` bounds `io` by ≈100 ms. The leaf timer is `sleep : Int -> IO Int` — an `IO` effect that parks for the given number of milliseconds and resumes with `0`. This unit is normative: a conforming implementation MUST interpret the argument as milliseconds. [S124 — partial; was Tested tests/concurrency_sleep.rs::sleep_parks_for_duration_then_resumes_and_continues, tests/concurrency_sleep.rs::sleep_links_and_runs_through_link_mode (evidence delta §14.14, row 75)]

**Empty `select`.** `(select [])` has no branch that can win. The runtime MUST raise a panic with message `select over empty collection` when the node runs, rather than return a synthesised value or hang. The panic ends the process in every mode (§12.7; user ruling, 2026-11-15).

**Relationship to the observational-equivalence guarantee.** Like a detached strand (§10.12.7), the control combinators are the **explicit-control** half of the model and are **NOT** part of the §10.12.1–§10.12.5 sequential-equivalence guarantee. That guarantee covers the *inferred* half, where every effect runs to completion and the only freedom is ordering/overlap of independent effects. A combinator deliberately **abandons** an effect (the loser, the timed-out work): the set of completion side-effects a program produces is **not** the same as running every branch to completion sequentially — which is exactly the point, and is the program's explicit choice. The combinators' value-level result is well-defined (item 1); what steps outside sequential-equivalence is the cancellation of the abandoned branches (§10.12.9). See [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation).

### 10.12.9 Structured Cancellation [Uncovered S122]

> **Superseded failure policy (2026-11-28):** the panic/runtime-error or
> platform-failure policy below is subject to [S125-Q12](appendix-d-open-questions.md#s125-q12-what-happens-when-a-macro-clause-raises-an-otherwise-unspecified-hardware-trap).
> The older wording is retained pending the next-sprint rewrite.

Cancellation is the load-bearing semantics underneath §10.12.8: when a `race`/`select` loser, a `timeout`'d effect, or an effect executing within either of them is **cancelled**, what a program may and may not observe of it is fixed. Cancellation is **not** a standalone user combinator — there is no `cancel` function and no user-installable handler. It is the *consequence* of the program's effect structure abandoning work (a branch losing a race, a timer firing); the program expresses cancellation only by the structure of the combinators above.

**Cancellation context.** Every effect executes within a cancellation context, determined when the effect is **executed** — not where its `IO` value was constructed, and not by the function calls that produced it.

- The program's top-level effect executes in the root context.
- Executing `primitives/select` gives each branch its own context, nested within the context in which it executes. The library derivations `race` and `timeout` create branch contexts through their underlying `select` composition (§10.12.8).
- A branch's context is cancelled when that branch loses, or when the `timeout` timer fires first. Cancelling a context cancels every context nested within it.
- Cancelling a context cancels every in-flight effect executing within it, however the implementation schedules that effect — inline, on a worker, or as a detached strand launched within it (§10.12.7 item 5).
- Only execution of this core first-completion composition establishes branch contexts; library wrappers inherit it through `primitives/select`. Function calls and returns, `primitives/bind` sequencing and inferred scheduling (§10.12.1–§10.12.7) neither establish nor cancel a context.
- A context is not cancelled by its branch completing. When a branch wins, or a `timeout`'d effect completes first, detached strands launched within that branch keep running; they are cancelled only if a context enclosing the combinator is later cancelled.

**Observable contract.** When an in-flight effect is cancelled:

| # | Requirement | Status |
|---|---|---|
| 1 | **Resources release.** Every resource the cancelled effect held MUST be released: a resource-capacity **permit** it acquired (§10.12.4.1) is returned to its token pool, and any reactor interest it registered (an fd-readiness wait, a timer) is deregistered. Releasing the permit is observable: a permit freed by a cancelled effect MUST become available to an effect parked on that token (the (N+1)th of §10.12.4.1 can then proceed). A program MUST NOT be able to exhaust a token pool by cancelling effects on it. | [S96] |
| 2 | **No completion side-effect.** A cancelled effect MUST NOT produce its **completion** side-effect: the value it would have computed is never returned, and any effect it had not yet performed at the cancellation point does not occur. Side-effects it had **already** performed before cancellation are **not** undone (cancellation is not a transaction/rollback) — the contract bounds *future* observation, not the past. What a program can observe of a cancelled effect is therefore exactly: whatever it had already done before the cancellation point, and nothing after. | [S96] |
| 3 | **Cancellation is not a fault.** A cancelled effect does not raise a runtime panic (§12.7.2) into the cancelling context, and cancellation does not invoke panic termination (§12.7). The winner's value (or `None`, for `timeout`) is the only result the combinator yields; cancellation of the losers is silent at the value level (it surfaces only through the dev-facing observability stream of §10.12.6 — a `cancellation` event). | [S96] |
| 4 | **Cleanup runs.** Cancellation releases the cancelled computation's live heap values through ordinary drop glue (§12.7) as its strand is torn down; reference counts are decremented and freed exactly as on normal completion. Cancellation MUST NOT leak the cancelled effect's resources (this is items 1 + 4 together: the permit, the reactor interest, and the heap). | [S96] |

This contract is **observational and mechanism-neutral**: it constrains what a program observes of a cancelled effect — that its resources free, that its completion side-effect does not occur, that it raises no fault — not how the runtime tears the effect down. A conforming implementation realises cancellation by dropping the in-flight future (releasing its acquired permit and deregistering its reactor interest as part of that drop); see [§12.4.4](12-runtime.md#1244-structured-control-combinators-and-cancellation) and `design/arch/effect-concurrency.md` §9. The permit-release and reactor-interest-deregistration on cancellation are the runtime obligations this observable surface rests on.

### 10.12.10 Reference Control Patterns — Graceful Shutdown and Cancel-on-Disconnect [Uncovered S122]

> **Superseded failure policy (2026-11-28):** the panic/runtime-error or
> platform-failure policy below is subject to [S125-Q12](appendix-d-open-questions.md#s125-q12-what-happens-when-a-macro-clause-raises-an-otherwise-unspecified-hardware-trap).
> The older wording is retained pending the next-sprint rewrite.

The combinators (§10.12.8) and cancellation (§10.12.9), composed with launch-and-continue (§10.12.7) and the process-exit panic rule (§12.7.9), give control patterns for a long-running server; a runtime panic still ends its process (user ruling, 2026-11-15). These are **derived patterns**, not new primitives; the library names are illustrative and this subsection states the observable consequences of their core composition because they are the user-facing reason the control half is a committed deliverable (§1 of `design/arch/effect-concurrency.md`).

| Pattern | Built from | Observable contract | Status |
|---|---|---|---|
| **Per-request timeout** | `timeout d handler` | A request handler that does not complete within *d* is cancelled (§10.12.9): its permit and reactor interest free, its remaining effect does not occur, and the request receives a timeout outcome (`None`) rather than hanging indefinitely. The server continues serving other requests. | [S96] |
| **Cancel-on-disconnect** | `race handler (await-disconnect conn)` | A handler racing against the connection's disconnect-detection effect is **cancelled** when the client disconnects first: the now-pointless work stops (§10.12.9), freeing its permit so a live request may use it. A disconnected client's handler MUST NOT continue to consume a resource permit to completion. | [Uncovered S122 — no platform provides a disconnect-detection effect, so no program can construct the pattern; the web survivor test observes only continued service; carried by ACT-0977] |
| **Graceful shutdown** | `race` of the server's work against the platform's shutdown-signal effect | When the shutdown signal wins, the server's work is cancelled together with the outstanding detached strands launched within it (the in-flight launched handlers; §10.12.7 item 5, §10.12.9): each releases its resources and stops producing further effects; the program then terminates with its in-flight work torn down cleanly rather than abandoned mid-effect or forced to run to completion. | [Uncovered S122 — no platform provides a shutdown-signal effect, and the launched-work cancellation the pattern composes (§10.12.7 item 5) is unevidenced; carried by ACT-0977] |

The observable invariant common to all three: **abandoned work releases its resources promptly and stops producing effects** (§10.12.9), so a server's resource pools (§10.12.4.1) are not pinned by work no one is waiting for. The mechanisms by which a program detects a disconnect or receives a shutdown signal are platform effects (ordinary `IO`, §10.10) and are implementation-/platform-defined; this subsection constrains only the cancellation observable that results from composing them with the combinators.
