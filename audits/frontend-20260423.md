# Frontend Crate Audit — 2026-04-23

Scope: `crates/cranelisp-frontend/` (`reader.rs`, `ast_builder.rs`, `module_extract.rs`, `quasiquote.rs`, `defmacro.rs`, `lib.rs`)

Quality dimensions assessed: **clarity, simplicity, duplication of code/code-paths**, with the goal of judging **maintainability and extensibility**.

Evidence basis:
- Static review of crate source (~7.1k LOC total)
- File size snapshot: `ast_builder.rs` 2915 LOC, `reader.rs` 1646, `defmacro.rs` 931, `module_extract.rs` 850, `quasiquote.rs` 680
- `cargo nextest run -p cranelisp-frontend`: **234/234 passing**

## Executive summary

The frontend crate is **functionally strong but structurally uneven**.

Its strengths are:
- clear separation by responsibility at the file level
- very good test coverage and spec-facing unit tests
- mostly direct, unsurprising parsing/building logic
- few abstraction layers, which keeps many paths easy to trace

Its main maintainability risks are:
1. **`ast_builder.rs` is too large and is now the crate’s dominant complexity sink**.
2. **There is meaningful duplication in dispatch and Sexp-construction code paths**, especially where small local conveniences have scaled into parallel mini-frameworks.
3. **Documentation and implementation have drifted**, including at least one major design mismatch: the frontend plan says `peg` was chosen, but the implementation is hand-written recursive descent.
4. **Several critical invariants are implicit rather than crate-local documented**, which creates agent traps and future refactor risk.

Overall assessment: **good current correctness, moderate future change risk**. The crate is maintainable today because the tests are strong and the code is still mostly straightforward; it is not yet shaped to remain easy to extend as macro/module/type syntax grows.

---

## What is working well

### 1. Responsibility boundaries are mostly clean

The crate splits into sensible files:
- `reader.rs`: text → `Sexp`
- `quasiquote.rs`: Sexp → Sexp macro-template lowering
- `defmacro.rs`: defmacro parsing + synthesized Sexp generation
- `module_extract.rs`: module/import/export/platform extraction
- `ast_builder.rs`: Sexp → AST

That top-level partition is good. A new contributor can usually find the right file quickly.

### 2. The code prefers directness over cleverness

Most functions do one obvious thing: read a form, parse a declaration, build an AST node, or synthesize a small Sexp fragment. This helps clarity. The reader in particular is readable despite being hand-written.

### 3. Tests materially de-risk refactoring

The crate’s strongest quality attribute is its test suite. 234 unit tests passing gives good behavioral protection, especially around edge cases in lexical precedence, quasiquote behavior, module extraction, and AST shape.

### 4. Error messages are generally explicit and local

Many paths return targeted parse/module errors close to the source of failure. This is better for maintainability than burying errors in generic helpers.

## Main findings

## 1. `ast_builder.rs` is carrying too much policy in one file

This is the highest-impact maintainability issue.

Evidence:
- ~2915 LOC
- ~142 functions
- multiple 40–90 line functions
- mixed responsibilities: top-level form dispatch, expression lowering, trait/impl lowering, type-expression parsing, annotation parsing, vector literals, test helper lowering, and a very large in-file test module

Why this matters:
- new language forms will keep accumulating here
- related logic is hard to locate because the file is organized by syntactic family, not by subsystem boundaries
- there are already signs of “parallel parsers” inside the file: top-level handling, expression handling, annotation handling, deftrait/impl handling, and special test/trace forms each evolve independently

Clarity impact: moderate-high

Simplicity impact: high

Extensibility impact: high — this file is where new syntax/features are most likely to land, so structural debt compounds fastest here.

## 2. Top-level dispatch is duplicated between batch and REPL entry paths

`build_repl_input()` and `build_top_level()` contain nearly the same logic:
- reject pre-AST forms
- reject non-ring0 toplevel forms
- handle `impl`
- handle `defn` / `deftype` / `deftrait` via `parse_def_visibility`
- otherwise fall through to expression building

This is not catastrophic duplication, but it is the kind that causes drift because one path eventually learns a new form before the other.

This is already a code-path quality issue: the crate conceptually has **one top-level form classifier**, but it is implemented twice.

## 3. Syntax recognition and syntax lowering are partially split, partially scattered

The codebase has good file-level separation, but inside files the same concepts recur in slightly different shapes:
- `reader.rs` recognizes special forms lexically
- `quasiquote.rs` recognizes quoted/unquoted list shapes again
- `defmacro.rs` synthesizes Sexp that must match `ast_builder.rs`’s expectations exactly
- `ast_builder.rs` then rejects some forms that “should have been handled earlier”

This architecture is valid, but the coupling is implicit. Example traps:
- `defmacro.rs` knows `build_annotated_params()` expects `:` + type-expr + name as separate bracket items
- `module_extract.rs` rewrites `super` eagerly, so downstream code must never assume literal `super` survives
- `lib.rs` warns that unexpanded macro calls reaching the AST builder become generic applications and fail later

These are not bugs; they are **hidden pipeline contracts**. Hidden contracts reduce extensibility because changes in one file require detailed knowledge of another file’s private expectations.

## 4. Sexp-construction code is repetitive and ad hoc

`quasiquote.rs` and `defmacro.rs` both build a lot of raw `Sexp::List` / `Sexp::Symbol` / `Sexp::Bracket` trees manually.

Examples:
- constructor helpers in `quasiquote.rs` (`make_sexp_sym`, `make_sexp_int`, `make_sexp_container`, `make_slist`, `make_sconcat`)
- match/constructor synthesis in `defmacro.rs` (`make_scons_match`, `make_match_sexp`, `make_match_sexp_exhaustive`, bracket destructuring builders)

This is readable in isolation, but the crate now has multiple local DSLs for “emit synthetic Sexp.” That increases duplication and makes refactors brittle, because the correctness of emitted forms depends on matching `ast_builder` and later stages exactly.

## 5. Documentation drift is now a real clarity problem

Two notable examples:
- `plan-frontend.md` documents a decision to use **`peg` 0.8**, but the reader is a **hand-written recursive descent parser**.
- `ast_builder.rs` file header still frames the file as largely Ring 0 and “non-Ring-0 rejected,” while the implementation now handles far more: traits, impls, strings, vec literals, trace/test forms, etc.

This is bigger than cosmetic drift. For maintainers and agents, stale design docs create false mental models and invite incorrect edits.

## 6. Tests are excellent, but file-local test bulk now obscures production structure

The test quality is a strength, but the largest files are also carrying very large inline test modules. For example, `ast_builder.rs` and `reader.rs` are both substantially expanded by tests. This raises scroll cost and makes production code structure harder to read.

I would not move these to sparse integration tests; the unit-test locality is useful. But the current layout is starting to work against readability.

## Recommended remediations, in priority order

## 1. Split `ast_builder.rs` by subsystem

**Highest impact recommendation.**

Suggested split:
- `ast/top_level.rs` — defn/deftype/deftrait/impl entry forms
- `ast/expr.rs` — expressions and special forms
- `ast/types.rs` — type-expression + annotation parsing
- `ast/patterns.rs` — pattern and match-arm builders
- `ast/common.rs` — `expect_*`, docstring helpers, visibility parsing

Why this matters most:
- directly reduces the largest complexity hotspot
- makes ownership clearer for future changes
- turns hidden coupling into explicit module boundaries

Agent guidance to add with this change:
- “Add new syntax in exactly one dispatch layer; do not update REPL and batch dispatch separately.”

## 2. Introduce a single top-level form classifier

Refactor `build_repl_input()` and `build_top_level()` to share one internal classifier, e.g.:
- `classify_top_level_form(...) -> TopLevelFormKind`
- then separate wrappers for batch vs REPL policy

Why:
- removes duplicate code-paths
- prevents batch/REPL drift
- makes future additions like `defmacro`, module forms, or new declarations safer

## 3. Add a crate-local `CLAUDE.md` (or equivalent living note) for frontend invariants

The frontend crate currently has no local guidance file. It should document the non-obvious invariants that span files:
- macro expansion must occur before AST building
- `module_extract` rewrites `super` at the frontend boundary
- all synthetic spans must come from the shared synthetic-span allocator
- emitted synthetic Sexp must match AST-builder syntax exactly
- comments may be preserved only on the dedicated parse path

This is the best agent-guidance remediation because it prevents false simplifications.

## 4. Centralize synthetic Sexp construction helpers

Create a small internal module for common synthetic Sexp builders used by `quasiquote.rs` and `defmacro.rs`.

Not everything should be unified, but common constructors and list/bracket/match helpers should stop being hand-recreated in multiple places.

Goal:
- reduce accidental syntax mismatches
- make synthetic output more obviously canonical
- shrink the amount of low-value boilerplate in macro-related code

## 5. Refresh or replace stale design docs immediately

At minimum:
- update `plan-frontend.md` to match the current implementation
- add short design notes for the hand-written reader, quasiquote lowering, and macro synthesis contracts
- update misleading module headers in `ast_builder.rs`

This is low effort, high leverage.

## 6. Keep unit tests local, but move large test blocks into submodules/files

Suggested shape:
- `reader_tests.rs`
- `ast_builder_tests/{expr.rs, top_level.rs, types.rs}`

This preserves locality while improving production-code readability.

---

## Specific traps to highlight for future agents

1. **Do not “simplify” away the macro-expansion-before-AST invariant.** If unexpanded macro forms reach the AST builder, failures become indirect and harder to diagnose.
2. **Do not introduce ad hoc synthetic spans.** Use the shared allocator so quasiquote/defmacro output stays globally unique.
3. **Do not reintroduce literal `super` downstream of `module_extract`.** The frontend boundary already normalizes it.
4. **Do not add a new top-level form in only one of REPL or batch entry paths.** The current structure makes this easy to do accidentally.
5. **Do not trust `plan-frontend.md` as implementation truth until it is refreshed.** It currently describes a materially different parser architecture.

---

## Bottom line

The frontend crate is **correct and serviceable**, with particularly strong tests and reasonable file-level decomposition. Its main weakness is that the successful accumulation of features has outgrown some of its original structure, especially in `ast_builder.rs`, and some cross-file contracts are now too implicit.

If only three remediations are funded, they should be:
1. split `ast_builder.rs`
2. unify top-level dispatch/classification
3. add crate-local guidance for frontend-specific invariants

Those three changes would produce the biggest long-term improvement in **clarity, simplicity, and resistance to duplicated code-paths**.
