# Integration Crate Audit (`src/`) — 2026-04-23

> **Sprint 63 supersession note (2026-05-02).** This audit is a point-in-time assessment, NOT ongoing ground truth. Target-direction sections are superseded by Decisions 38, 39, 40, 41, 42 (see `design/arch/decisions/`). Current-state sections remain authoritative as historical observation of the codebase at the audit date. Per substance-scoping §1.5, audits are point-in-time opinions; `/review` is the continuous-audit role going forward, evaluating implementation against the post-Sprint-63 canonical set rather than against this audit's target-direction.


**Scope**: top-level integration/orchestration code in `src/` — especially `session_v4.rs`, `worker.rs`, `scheduler.rs`, plus supporting modules (`pipeline.rs`, `session.rs`, `main.rs`, `platform.rs`, `expander.rs`, `observability.rs`, `save.rs`, `exe.rs`, `lib.rs`).

**Quality dimensions**: clarity, simplicity, lack of duplicated code and code-paths, maintainability, extensibility.

**Method**:
- direct review of `src/*.rs`
- structural metrics
- follow-up review of target-state dependency-crate diagrams:
  - `audits/frontend-20260423-target-state.mmd`
  - `audits/typecheck-20260423-target-state.mmd`
  - `audits/backend-20260423-target-state.mmd`

## Executive summary

I audited the integration layer, not the child crates themselves. The key conclusion is:

> **`src/` is doing too much policy work and carries too many parallel orchestration paths for a layer whose long-term role should be coordination.**

The dependency-crate target-state diagrams all point toward the same shape:
- frontend → thin facade, shared classifier, canonical internal helpers
- typecheck → single `check()` pipeline, shared walkers, centralized lookups
- backend → thin facade, canonical compile entrypoint, canonical cache API

Against that backdrop, the integration layer should ideally become a **thin coordinator over those crate facades**.

Instead, today `src/` is:
- a scheduler implementation
- a worker runtime
- a REPL command engine
- a macro-expansion runtime bridge
- a cache orchestrator
- a file-watcher / backing-file synchronizer
- a trace/test runner bridge
- a linker/executable orchestrator
- and, in places, a second home for logic that conceptually belongs in narrower crate-local authorities

This does not mean the code is bad. Much of it is thoughtful and heavily tested. But the integration crate has become the project’s **complexity sink**.

**Overall assessment**:
- **Clarity**: moderate; many functions are understandable locally, but authority is spread across too many files and too many “mirrored” flows
- **Simplicity**: moderate-low at crate scale; the orchestration model is richer than the current file structure can carry cleanly
- **Duplication of code/code-paths**: high enough to be the main maintainability concern
- **Maintainability trajectory**: risky unless `src/` is made more facade-like and less policy-heavy

## What is working well

### 1. The intended architecture is coherent
The v4 direction is clear: one `CompilerSession`, scheduler-driven workers, one batch/link/REPL family, and symbol tables as the durable source of truth. The code is not directionless.

### 2. Some boundaries are conceptually strong
There are good ideas already present:
- `scheduler.rs` owns coordination state
- `worker.rs` owns priority-worker processing
- `session_v4.rs` owns session lifecycle and REPL experience
- `pipeline.rs` holds reusable evaluation helpers

The problem is not lack of decomposition; it is that the decomposition is no longer **tight enough** for the amount of policy now present.

### 3. The code documents invariants aggressively
This layer is full of rationale and defect-history comments. That is useful because the code is managing real concurrency, cache-ordering, and JIT lifetime hazards. The issue is not absence of documentation; it is that the documentation is often embedded as historical narrative inside already-large files.

## Findings

### Finding 1 — `session_v4.rs` is a god-file for the integration layer
**Impact: High**

At **5,417 LOC** with **149 functions** and **23 functions ≥60 lines**, `session_v4.rs` now carries too many responsibilities:
- session construction / shared-state seeding
- REPL command parsing and help text
- REPL eval
- dependency registration for eval
- file watching / reload flow
- introspection formatting
- trace/test extern setup
- worker lifecycle / nice-worker flow
- link and object-code flush control
- a very large in-file test body

This is the integration crate’s clearest maintainability risk.

The issue is not merely file size; it is **mixed authority**. REPL UX, concurrency coordination, dependency publication, evaluation, and object worker management all live in one place.

**Why it matters**
- every new integration feature tends to land here
- change review requires holding too many unrelated invariants in mind
- future refactors are likely to preserve the blob because everything depends on everything else

### Finding 2 — `worker.rs` is a second god-file, and together with `session_v4.rs` it creates a split-brain integration model
**Impact: High**

`worker.rs` is **5,041 LOC**, with **33 functions ≥60 lines**. It owns:
- macro resolution / on-demand macro compilation
- module form processing
- dependency discovery / registration
- cache-hit loading
- JIT setup and inline codegen
- priority worker loop
- parts of platform loading and structural declaration handling

Many comments explicitly say functions **mirror** or are **shared cores** of other paths. That is a strong signal that the code has converged functionally but not structurally.

Examples in the source/comments:
- `compile_macro_clause_with_state` / `compile_macro_clause_inline`
- `collect_jit_setup_public` “mirrors the setup used inside `inline_jit_codegen_for_module`”
- several code paths around dependency registration / publish-before-register
- several tests “mirror the exact routing loop” or “mirror the exact store call”

This is valuable evidence: the system has canonical behavior in mind, but not yet a single home for it.

### Finding 3 — dependency registration and publish-before-register discipline still spans multiple authorities
**Impact: High**

The dependency-registration protocol is one of the hardest parts of the integration layer, and it is still split across:
- worker-side `register_dep` / `publish_dep_sexps` / `handle_import`
- session-side `register_dep_for_eval`
- scheduler-side expectations about registration order and pool placement

The code comments make this explicit. The protocol is carefully defended, but not encapsulated in one authority.

That is a maintainability problem because the most delicate invariants are the least centralized.

**Why it matters**
- ordering bugs reappear when the protocol is changed in one path and not another
- the REPL/eval path and worker path must remain behaviorally identical
- agent edits are high-risk because the “right” place to change this is not obvious

### Finding 4 — worker orchestration is split across files in a way that obscures ownership
**Impact: Medium-High**

Today:
- priority worker loop lives in `worker.rs`
- nice worker loop lives in `session_v4.rs`
- object compilation helper also lives in `session_v4.rs`
- scheduler state lives in `scheduler.rs`

That is serviceable, but it weakens clarity. The worker model is conceptually one subsystem; its implementation is split by historical evolution.

This is the kind of structural split that makes future simplification harder, because “worker ownership” is no longer obvious.

### Finding 5 — `src/lib.rs` is not a thin facade; it exports almost the whole kitchen sink
**Impact: Medium-High**

`src/lib.rs` publicly exports **18 modules**. The integration crate is therefore not presenting a narrow public surface; it is exposing its internal decomposition directly.

That is the opposite of the direction implied by the frontend/typecheck/backend target-state diagrams.

**Why it matters**
- tests and callers can couple to internals rather than stable integration APIs
- refactoring internals becomes expensive because visibility is broad
- the crate cannot easily become a simpler orchestration facade while everything is public

### Finding 6 — legacy/transitional structure remains visible in production shape
**Impact: Medium**

There are still visible layers of “new canonical path + compatibility/transitional helper” in `src/`:
- `session.rs` still owns utility/config/cache pieces while `session_v4.rs` owns the actual session
- `pipeline.rs` contains reusable evaluation helpers, but key eval orchestration still lives in `session_v4.rs`
- comments in `session_v4.rs` still describe wrapping an “existing CompilationSession” even though v4 is now the real session model

None of these are individually alarming, but together they make the integration layer feel partially converged rather than settled.

### Finding 7 — historical commentary is useful, but too much of it now lives inline in production hot paths
**Impact: Medium**

A lot of code in `src/` carries sprint-wave provenance, defect narratives, and architecture review notes inline. The comments are often excellent, but they also increase scan cost substantially, especially in already-large files.

This is not a request to delete rationale. It is a recommendation to move some of the longer historical narratives into design notes and leave shorter invariant comments in code.

## Cross-crate simplification lens from the child-crate target states

After reading the frontend/typecheck/backend target-state `.mmd` files, the clearest implication for `src/` is:

> **As child crates simplify around canonical facades, the integration layer should lose internal policy, not accumulate more.**

The child crates’ target states assume:
- frontend gives a thin parse/expand/build facade
- typecheck gives a thin check/check_form facade
- backend gives a thin compile facade

If those plans land, `src/` should become mostly:
- wiring
- lifecycle
- scheduler coordination
- user-facing session behavior

Right now `src/` still contains a lot of logic that is “between” facade and implementation. That is the maintainability gap.

## Recommended remediations, in priority order

### 1. Split `session_v4.rs` by responsibility
**Highest impact**

Suggested split:
- `session_v4/core.rs` — `CompilerSession`, `SharedState`, lifecycle
- `session_v4/repl.rs` — slash commands, help, prompt, formatting
- `session_v4/eval.rs` — eval / codegen-and-execute / dep-retry loop
- `session_v4/reload.rs` — watcher, reload, backing-file regeneration
- `session_v4/object.rs` — nice worker loop and object compilation
- `session_v4/tests/` — large test sections

This is the single most valuable structural cleanup.

### 2. Introduce one canonical dependency-registration service
Encapsulate the publish-before-register / cache-hit / source-stash / scheduler-registration protocol behind a single internal API used by both:
- worker dependency discovery
- REPL/session-side blocked-dependency recovery

Today this protocol is carefully defended but still split. It should exist in one place only.

### 3. Unify worker orchestration into one subsystem
Bring priority-worker and nice-worker loop ownership together. Whether the final home is `worker.rs` or a new `workers/` subtree matters less than making one subsystem authoritative.

### 4. Narrow `src/lib.rs` into an actual facade
Prefer exposing a small stable surface such as:
- `session_v4::CompilerSession`
- selected formatting helpers genuinely needed by tests
- maybe a small number of orchestration entrypoints

Most modules in `src/` should not need to be public.

### 5. Move long historical narratives from code into design notes / local guidance
Keep invariant comments in code, but move long sprint-history explanations out of the hot path where possible.

This would materially improve readability without losing knowledge.

## Guidance for future agents / maintainers

1. **Do not add new integration behavior directly to `session_v4.rs` by default.** First decide which subsystem owns it: session core, REPL UX, eval, reload, object workers, or scheduler.
2. **Do not duplicate the dependency-registration protocol.** If a new path needs “publish parsed forms + register + wait/unblock”, factor it into the canonical helper.
3. **Do not split worker behavior across session/worker files further.** The current split is already larger than ideal.
4. **Do not widen `src/lib.rs` exports.** Move toward a thinner facade, not a broader one.
5. **When a comment says a function “mirrors” another path, treat that as a design smell.** Prefer extracting the shared authority.
6. **Preserve concurrency invariants, but prefer moving rationale to design docs once the mechanism is stable.** Inline comments should describe the invariant, not the whole sprint history.

## Bottom line

The integration layer is the repository’s current structural bottleneck.

The main issue is not correctness. It is that `src/` — especially `session_v4.rs` and `worker.rs` — is carrying too much detailed policy for a layer that should increasingly act as a **thin coordinator over clearer crate interfaces**.

If only three actions are funded, they should be:
1. **split `session_v4.rs` by responsibility**
2. **centralize dependency registration/order invariants in one authority**
3. **narrow `src/lib.rs` and unify worker ownership**

Those changes would do the most to improve **clarity, simplicity, and resistance to duplicated code-paths** in the integration code going forward.
